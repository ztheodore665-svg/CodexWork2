## 1. 项目背景与目标

### 1.1 背景

雄安新区容东片区采用"窄路密网"路网结构——道路宽度较窄、交叉口间距小、路网密度高。这种结构下，传统单点信号优化效果有限，需要多层次的交通调度策略。

### 1.2 目标

构建一个交通调度算法仿真与可视化平台，具备以下能力：

1. 加载目标区域networks，运行微观交通仿真
2. 实现三套不同层次的交通调度算法，可在运行时动态切换
3. 实时可视化路网状态、车辆位置、信号灯状态
4. 采集和展示仿真指标，用于算法效果评估
5. 支持容器化部署

### 1.3 三套调度方案概述

| 方案 | 名称 | 核心思路 | 适用场景 |
|------|------|----------|----------|
| 方案一 | 分时多算法切换 | 按时段选择不同信号配时，主干道绿波协调 | 基础场景，低实施成本 |
| 方案二 | 实时观测自适应 | 多智能体强化学习实时控制信号，交通流预测辅助 | 高需求场景，需训练模型 |
| 方案三 | 受限车队路线引导 | 对公交/网约车等车队车辆提供动态路线引导 | 车队管理场景 |

## 2. 系统总体需求

### 2.1 系统组成

系统分为三个主要部分：

1. **仿真引擎层**：负责微观交通仿真，提供路网加载、车辆生成、车辆运动、信号灯控制等能力
2. **后端服务层**：负责仿真管理、算法调度、数据采集、对外提供 API 和实时推送
3. **前端展示层**：负责路网可视化、车辆渲染、控制交互、指标展示

### 2.2 数据流

```
前端  ←实时推送→  后端  ←控制接口→  仿真引擎
  ↕ REST API         ↕ 内部调用
  └─── HTTP ─────────┘
```

- 前端通过 REST API 发出控制指令（启动/暂停/停止仿真、切换方案、配置参数）
- 后端通过实时推送通道向前端推送车辆位置、信号灯状态、指标数据
- 后端通过仿真引擎的控制接口读取路网状态、写入信号配时、设置车辆路线

### 2.3 并发模型

- 仿真在独立线程中运行，主线程处理 API 请求和实时推送
- 多个前端客户端可同时连接，共享同一仿真会话
- 算法决策在仿真线程中执行，API 线程可查询算法状态

## 3. 仿真环境需求

### 3.1 networks

#### 3.1.1 路网来源

需要雄安容东片区的networks，来源为 OpenStreetMap 格式的地图数据。系统需提供从 OSM 数据转换为仿真路网文件的能力。

#### 3.1.2 路网结构要求

路网需包含以下要素：

| 要素 | 说明 |
|------|------|
| 道路段（edge） | 每条 edge 有唯一 ID、起止节点、车道数、限速、长度、道路类型 |
| 交叉口（node/junction） | 每个交叉口有唯一 ID、坐标、类型（信号控制/无信号/让行） |
| 信号灯（traffic light） | 部分交叉口关联信号灯，每个信号灯有唯一 ID、相位定义、配时方案 |
| 车道（lane） | 每个 edge 包含一条或多条车道，每条车道有唯一 ID |

#### 3.1.3 道路类型分类

| 类型 | 说明 | 典型限速 |
|------|------|----------|
| arterial（主干道） | 区域内主要道路，承担干线交通 | 50-60 km/h |
| secondary（次干道） | 区域内集散道路 | 40-50 km/h |
| local（支路） | 窄路密网中的小尺度道路 | 30-40 km/h |

#### 3.1.4 路网导出

系统需将仿真路网导出为 GeoJSON 格式（FeatureCollection），供前端渲染。每个 edge 导出为一条 LineString Feature，包含 edge_id、from_node、to_node、lanes、speed_limit、length、road_type 属性。交叉口导出为坐标点列表，包含 node_id、坐标、tls_id（如有）、type。

#### 3.1.5 路网摘要统计

系统需提供路网摘要信息：

| 统计项 | 说明 |
|--------|------|
| edge_count | 路段总数 |
| intersection_count | 交叉口总数 |
| tls_count | 信号灯总数 |
| total_lane_length_km | 车道总长度（km） |
| network_density_km_per_km2 | 路网密度（km/km²） |

### 3.2 交通需求生成

系统需提供交通需求生成能力：

1. 支持生成随机 OD（起讫点）需求，车辆从随机起点出发前往随机终点
2. 支持设定车辆总数、生成时间跨度
3. 支持多种车辆类型（小客车、公交、货车、自行车等）
4. 支持按时间分布生成需求（如高峰时段车辆更多）
5. 生成结果为路线文件，包含每辆车的 ID、类型、出发时间、路线

### 3.3 信号配时生成

系统需提供初始信号配时方案生成能力：

1. 为所有信号控制交叉口生成默认配时方案
2. 支持生成不同时段的配时方案（早高峰/平峰/晚高峰/夜间）
3. 支持生成绿波协调配时（主干道沿线交叉口绿灯偏移对齐）
4. 配时方案包含相位定义、绿灯时间、黄灯时间、全红时间

### 3.4 仿真控制

#### 3.4.1 仿真生命周期

| 状态 | 说明 | 允许的转移 |
|------|------|-----------|
| idle | 未启动 | → running |
| running | 运行中 | → paused, → stopped, → error |
| paused | 已暂停 | → running, → stopped |
| stopped | 已停止 | → idle |
| error | 错误 | → idle |

#### 3.4.2 仿真参数

| 参数 | 说明 | 默认值 |
|------|------|--------|
| step_length | 仿真步长（秒） | 1.0 |
| begin_time | 仿真开始时间（秒） | 0 |
| end_time | 仿真结束时间（秒） | 86400（24小时） |
| speed | 速度倍率 | 1.0（实时） |

#### 3.4.3 仿真控制能力

- **启动**：加载路网配置文件，启动仿真引擎，初始化选定的调度方案
- **暂停/恢复**：暂停后仿真停止推进，恢复后继续
- **停止**：终止仿真，释放资源，回到 idle 状态
- **步进**：在暂停状态下手动推进 N 步
- **调速**：运行时动态调整仿真速度倍率（0=暂停，1=实时，N=N倍速）
- **会话管理**：每次启动生成唯一 session_id，支持查询当前状态

#### 3.4.4 仿真引擎接口需求

后端需要通过仿真引擎的编程接口完成以下操作：

**读取类**：
- 获取所有 edge ID 列表
- 获取指定 edge 上的车辆数、平均速度、占有率
- 获取指定 edge 的旅行时间
- 获取所有车辆 ID 列表
- 获取指定车辆的位置（x, y）、角度、速度、所在车道、车辆类型、路线、等待时间
- 获取所有信号灯 ID 列表
- 获取指定信号灯的当前状态字符串、相位索引、相位数、已持续时间
- 获取信号灯控制的连接关系（相位与 incoming lane 的对应）
- 获取新进入路网的车辆列表、离开路网的车辆列表
- 获取累计到达车辆数

**写入类**：
- 设置信号灯当前相位
- 设置信号灯相位持续时间
- 切换信号灯配时方案
- 设置车辆路线
- 触发车辆重路由

### 3.5 数据采集

系统需在仿真运行过程中持续采集以下数据：

#### 3.5.1 车辆数据

每步采集所有车辆的位置、角度、速度、所在车道、等待时间。采用增量更新策略：记录新进入路网的车辆（added）、位置发生变化的车辆（updated，仅推送变化字段）、离开路网的车辆（removed）。

#### 3.5.2 信号灯数据

每步采集所有信号灯的当前状态。仅当信号灯状态发生变化时推送。

#### 3.5.3 全局指标

每 60 步采集一次全局指标：

| 指标 | 说明 | 计算方式 |
|------|------|----------|
| vehicle_count | 路网中车辆数 | 当前车辆总数 |
| avg_speed | 平均速度 (m/s) | 所有车辆速度均值 |
| avg_delay | 平均延误 (s/veh) | 自由流速度与实际速度之差的均值 |
| total_throughput | 累计通过车辆数 | 累计离开路网的车辆数 |
| avg_queue_length | 平均排队长度（辆） | 各交叉口排队车辆数的均值 |
| avg_waiting_time | 平均等待时间 (s) | 所有车辆等待时间的均值 |

#### 3.5.4 交叉口指标

每个信号控制交叉口采集：

| 指标 | 说明 |
|------|------|
| queue_length | 排队长度（辆） |
| waiting_time | 平均等待时间 (s) |
| throughput | 通过车辆数 |
| current_phase | 当前相位状态字符串 |
| phase_duration | 当前相位总时长 (s) |

#### 3.5.5 历史指标

系统需存储指标的时间序列，支持按时间范围和采样间隔查询。支持的指标名：avg_delay、avg_speed、throughput、queue_length。

## 4. 数据接口需求

### 4.1 REST API

所有 REST 接口前缀为 `/api/v1`，响应统一格式为 `{"code": 0, "data": {...}}`，错误时为 `{"code": 错误码, "message": "...", "data": null}`。

#### 4.1.1 networks接口

| 接口 | 方法 | 说明 |
|------|------|------|
| `/network` | GET | 获取路网 GeoJSON 数据 |
| `/network/summary` | GET | 获取路网摘要统计 |

#### 4.1.2 仿真控制接口

| 接口 | 方法 | 说明 |
|------|------|------|
| `/simulate/start` | POST | 启动仿真，指定配置文件路径、步长、调度方案等 |
| `/simulate/stop` | POST | 停止仿真 |
| `/simulate/pause` | POST | 暂停仿真 |
| `/simulate/resume` | POST | 恢复仿真 |
| `/simulate/step` | POST | 手动步进 N 步 |
| `/simulate/speed` | POST | 设置速度倍率 |
| `/simulate/status` | GET | 查询当前仿真状态 |

启动仿真时需指定：
- 仿真配置文件路径
- 仿真步长、开始时间、结束时间
- 调度方案选择（scheme_1 / scheme_2 / scheme_3 / none）
- 方案特定配置参数

#### 4.1.3 指标查询接口

| 接口 | 方法 | 说明 |
|------|------|------|
| `/metrics/realtime` | GET | 获取实时指标快照（全局+各交叉口） |

#### 4.1.5 健康检查

| 接口 | 方法 | 说明 |
|------|------|------|
| `/health` | GET | 健康检查，返回服务状态、版本、仿真状态、连接数 |

#### 4.1.6 错误码

| 错误码 | 含义 |
|--------|------|
| 0 | 成功 |
| 1001-1006 | 仿真相关错误（未启动/已在运行/状态不允许/配置不存在/启动失败/连接失败） |
| 2001-2002 | 路网相关错误（未加载/导出失败） |
| 3001-3003 | 方案相关错误（不存在/配置无效/模型不存在） |
| 4001-4002 | WebSocket 相关错误（格式错误/未知类型） |

### 4.2 实时推送（WebSocket）

#### 4.2.1 连接

前端通过 WebSocket 连接后端，连接后服务端发送 `connected` 消息，包含 session_id 和服务器时间。

#### 4.2.2 服务端推送消息

统一消息格式：`{"type": "消息类型", "data": {...}, "timestamp": 仿真步数}`

| 消息类型 | data 内容 | 推送频率 |
|----------|----------|----------|
| connected | session_id, server_time | 连接时一次 |
| simulation_step | step, simulation_time, vehicle_count, avg_speed | 每步 |
| vehicle_update | added(完整车辆), updated(变化字段), removed(ID列表) | 每步 |
| tls_update | {tls_id: 状态信息} | 状态变化时 |
| metrics_update | overall(全局指标) | 每 60 步 |
| simulation_event | event_type, message, details | 事件触发时 |

#### 4.2.3 客户端发送消息

| 消息类型 | data 内容 | 说明 |
|----------|----------|------|
| set_speed | speed | 设置速度倍率 |
| pause | - | 暂停 |
| resume | - | 恢复 |
| stop | - | 停止 |
| step | steps | 手动步进 |
| set_update_interval | vehicle_interval, tls_interval, metrics_interval | 调整推送频率 |
| set_viewport | min_x, max_x, min_y, max_y | 设置视域范围（视域裁剪） |

#### 4.2.4 视域裁剪

前端可设置视域范围（矩形坐标框），后端只推送视域范围内的车辆数据，减少数据传输量。传 null 取消视域限制。

#### 4.2.5 推送频率控制

前端可动态调整三类数据的推送间隔：
- 车辆数据推送间隔（步），默认 1
- 信号灯数据推送间隔（步），默认 1
- 指标推送间隔（步），默认 60

## 5. 调度算法需求

### 5.1 算法基类需求

所有调度方案需遵循统一的生命周期接口：

| 生命周期方法 | 调用时机 | 说明 |
|-------------|----------|------|
| init | 仿真启动后、第一步之前 | 初始化算法，构建内部数据结构 |
| on_step | 每个仿真步 | 执行算法逻辑（采集数据、做决策、应用控制） |
| on_metrics | 指标快照产生时（每60步） | 可选，用于记录算法效果 |
| handle_action | API 请求时 | 处理外部配置动作（切换模式、设置参数等） |
| cleanup | 仿真停止时 | 释放资源 |

算法需能向前端推送事件，事件包含：事件类型、描述消息、附加数据。

算法运行时上下文需包含：仿真引擎实例、信号灯控制器、车辆跟踪器、方案特定配置。

### 5.2 方案一：分时多算法切换（TOD + 绿波协调）

#### 5.2.1 功能概述

根据仿真时间自动切换信号配时方案，在高峰时段对主干道进行绿波协调。包含三个子模块：

1. **TOD 时段调度器**：根据时间确定当前时段，自动或手动切换
2. **Webster 最优配时优化器**：基于实时流量计算各交叉口最优信号配时
3. **MAXBAND 绿波协调器**：计算主干道沿线交叉口的绿灯偏移，实现绿波

#### 5.2.2 TOD 时段调度需求

**时段定义**：

| 时段 | 时间范围 | 周期范围 | 绿波 |
|------|----------|----------|:---:|
| 早高峰 morning_peak | 07:00-09:00 | 60-120s | 启用 |
| 平峰 off_peak | 09:00-17:00 | 80-150s | 不启用 |
| 晚高峰 evening_peak | 17:00-19:00 | 60-120s | 启用 |
| 夜间 night | 19:00-次日07:00 | 90-180s | 不启用 |

**功能要求**：
- 根据仿真时间自动检测时段过渡，过渡时触发配时重算
- 支持手动强制切换到指定时段（覆盖自动调度）
- 支持解除手动强制，恢复自动调度
- 支持自定义时段配置（时段范围、周期范围、是否启用绿波）
- 支持跨午夜时段（如夜间 19:00-07:00）

#### 5.2.3 Webster 最优配时需求

**功能要求**：
- 为每个信号控制交叉口建立"相位-edge"映射关系（每个相位控制哪些 incoming edge）
- 采集各 edge 的实时交通流量
- 按相位分组计算各相位的流量比 y_i = q_i / s_i（q=流量，s=饱和流量）
- 计算 Webster 最优周期：C = (1.5×L + 5) / (1 - Y)，其中 L=总损失时间，Y=Σy_i
- 分配各相位绿灯时间：g_i = (y_i / Y) × (C - L)
- 约束条件：周期 ∈ [40, 240]s，最小绿灯 8s，Y ≤ 0.95（过饱和保护）
- 支持批量生成所有交叉口的配时方案
- 将配时方案应用到仿真引擎

**流量采集方式**：
- 从仿真引擎获取各 edge 的车辆数、平均速度、占有率
- 基于占有率估算流量（近似方法）
- 占有率过低但有车辆时，用速度和 edge 长度估算流量

**饱和流量默认值**：

| 道路类型 | 饱和流量 (veh/h/lane) |
|----------|:---:|
| 主干道 | 1800 |
| 次干道 | 1600 |
| 支路 | 1400 |
| 默认 | 1600 |

**配时方案数据结构**：
- 周期长度
- 各相位配时（有效绿灯时间、黄灯时间、全红时间、损失时间、实际绿灯显示时间）
- 协调偏移量
- 总损失时间、总流量比
- 是否使用默认配时（无流量数据时）
- 生成时的仿真步数

#### 5.2.4 MAXBAND 绿波协调需求

**功能要求**：
- 自动检测走廊：沿同一方向的信号灯序列
- 计算走廊上相邻交叉口间的旅行时间
- 以旅行时间作为偏移量，使绿灯起始时间与车队到达时间对齐
- 计算绿波带宽（bandwidth）
- 将偏移方案应用到配时方案
- 支持手动添加走廊

**偏移计算**：
- 以走廊第一个交叉口为基准（offset=0）
- 后续交叉口的 offset = 累积旅行时间 mod 周期长度
- 绿波带宽 = 最小绿灯时间 - 偏移量范围

**走廊数据结构**：
- 走廊 ID、名称、方向（南北/东西）
- 节点列表（每个节点包含 tls_id、坐标、距起点距离、距上一节点旅行时间）
- 自由流速度

**走廊检测策略**：
- 获取每个信号灯的坐标位置
- 按坐标聚类寻找近似共线的信号灯序列
- 过滤过短的序列（< 2 个交叉口或 < 200m）
- 一个信号灯只属于一条走廊（选择最长的）
- 最多检测 10 条走廊

**统一周期**：
- 绿波协调需要统一周期长度
- 取所有交叉口的最大周期，对齐到 5 的倍数
- 按比例调整各交叉口的绿灯时间

#### 5.2.5 方案一控制器需求

**初始化**：
- 初始化 TOD 调度器（默认或自定义时段配置）
- 初始化 Webster 优化器（建立所有 TLS 的相位-edge 映射）
- 初始化 MAXBAND 协调器（自动检测走廊）
- 执行首次配时计算

**每步逻辑**：
- 检查 TOD 时段是否过渡，过渡时触发配时重算
- 周期性重算（默认每 300 步，适应流量变化）

**支持的 API 动作**：

| 动作 | 说明 | 参数 |
|------|------|------|
| switch_tod_plan | 手动切换 TOD 时段 | plan_name |
| release_force | 解除手动强制时段 | - |
| recalculate | 强制重算配时 | - |
| enable_green_wave | 启用/禁用绿波 | enabled |
| add_corridor | 手动添加走廊 | corridor_id, name, direction, tls_ids, positions |
| get_status | 查询算法状态 | - |

**状态查询需返回**：
- 当前 TOD 时段信息
- 走廊检测结果
- 配时统计（交叉口数、默认配时数、平均周期、协调走廊数）
- 偏移方案详情
- 统计信息（时段过渡次数、重算次数、最后动作）

### 5.3 方案二：实时观测自适应（MAPPO + STGCN）

#### 5.3.1 功能概述

使用多智能体强化学习（MAPPO）实时控制信号灯，辅助以交通流预测（STGCN）。当强化学习模型不可用时，降级为 SCOOT-like 自适应控制。包含五个子模块：

1. **状态编码器**：为每个交叉口构建标准化的观测向量
2. **奖励计算器**：计算多层次的奖励信号
3. **STGCN 预测器**：短时交通流预测
4. **MAPPO 策略网络**：多智能体策略学习和推理
5. **SCOOT 降级控制器**：无模型时的自适应控制

#### 5.3.2 状态编码器需求

**观测空间设计（每个交叉口 agent）**：

每个交叉口的观测向量包含以下部分：

| 序号 | 数据项 | 说明 | 归一化方式 |
|------|--------|------|-----------|
| 1 | 当前相位 one-hot 编码 | 相位索引的独热编码 | 0/1 |
| 2 | 当前相位已持续时间 | 归一化到 [0,1] | elapsed / 60 |
| 3 | 各 approach edge 的排队长度 | halting 车辆数 | queue / 50 |
| 4 | 各 approach edge 的车辆数 | edge 上车辆总数 | count / 100 |
| 5 | 各 approach edge 的平均速度 | edge 平均速度 | speed / 13.89 |
| 6 | 邻居交叉口当前相位 | 归一化 | phase / max_phases |
| 7 | 全局平均速度 | 归一化 | speed / 13.89 |
| 8 | 全局车辆密度 | veh/m | density / 0.3 |

所有值归一化到 [0, 1]。

**观测维度计算**：
```
维度 = max_phases + 1 + 3×max_edges + max_neighbors + 2
```

**邻居关系构建**：
- 如果交叉口 A 的 outgoing edge 是交叉口 B 的 incoming edge，则 A 和 B 是邻居
- 每个交叉口最多保留 4 个邻居

**数据采集来源**：
- 排队长度：edge 上的 halting 车辆数
- 车辆数：edge 上的车辆总数
- 平均速度：edge 的平均速度
- 邻居相位：邻居交叉口的当前相位索引
- 全局平均速度：所有车辆速度均值
- 全局密度：总车辆数 / 总 edge 长度

#### 5.3.3 奖励函数需求

**分层奖励结构**：

```
R_total = w_local × R_local + w_global × R_global + w_coord × R_coord - switch_penalty
```

**局部奖励**：
```
R_local = -α × queue_length - β × waiting_time + γ × throughput
```
- 排队惩罚：归一化排队长度 × 权重
- 等待惩罚：归一化等待时间 × 权重
- 吞吐奖励：归一化平均速度 × 权重

**全局奖励**：
```
R_global = -δ × avg_delay - ε × avg_queue + ζ × avg_speed
```

**协调奖励**：
- 基于邻居相位一致性计算

**切换惩罚**：
- 每次相位切换扣除固定惩罚
- 1 分钟内切换频率超限时惩罚加倍

**默认权重**：

| 权重 | 默认值 | 说明 |
|------|--------|------|
| w_local | 0.5 | 局部奖励权重 |
| w_global | 0.3 | 全局奖励权重 |
| w_coord | 0.2 | 协调奖励权重 |
| queue | 1.0 | 排队惩罚系数 |
| waiting | 0.5 | 等待惩罚系数 |
| throughput | 0.3 | 吞吐奖励系数 |
| switch_penalty | 0.1 | 每次切换惩罚 |

**周期奖励（稀疏奖励）**：
- 在信号周期结束时计算，用于价值函数目标
- 基于周期内的平均排队、平均速度、全局速度

#### 5.3.4 STGCN 预测器需求

**功能要求**：
- 采集每条 edge 的历史交通特征（流量、速度、占有率）
- 预测下一时间步的交通流
- 支持三种工作模式：
  1. 模型推理模式：加载预训练模型
  2. 在线学习模式：运行时积累数据训练
  3. EWMA 降级模式：无模型时使用指数加权移动平均

**输入输出**：
- 输入：过去 12 步的所有 edge 的 3 维特征（流量、速度、占有率）
- 邻接矩阵：从路网拓扑构建（edge 之间的连接关系）
- 输出：下一时间步各 edge 的预测流量

**历史数据管理**：
- 每条 edge 维护固定长度（12 步）的历史队列
- 维护 EWMA 平滑值
- 计算流量趋势（上升/下降）

**降级策略**：
- 无深度学习框架时，使用 EWMA + 趋势修正
- 置信度基于历史数据量

#### 5.3.5 MAPPO 策略网络需求

**架构要求**：
- 所有交叉口 agent 共享同一个策略网络参数（parameter sharing）
- 中心化价值函数（Critic）使用全局状态
- 策略网络输入：单个 agent 的观测向量
- 价值网络输入：所有 agent 的观测拼接（全局状态）
- 动作空间：离散，选择下一个相位索引

**工作模式**：
1. 训练模式：有深度学习框架，在线训练
2. 推理模式：加载预训练模型，纯推理
3. 启发式模式：无深度学习框架，基于规则的策略

**启发式策略规则**（降级模式）：
- 当前相位持续时间 < 最小绿灯时间 → 保持
- 当前相位持续时间 > 最大绿灯时间 → 切换到下一相位
- 当前相位排队已清除且下一相位排队严重 → 切换
- 否则 → 保持

**经验存储**：
- 存储每步的（观测、全局状态、动作、奖励、对数概率、价值估计、是否结束）
- 经验回放缓冲区，容量 10000

**PPO 更新**：
- 每 300 步更新一次
- 计算 GAE（Generalized Advantage Estimation）
- PPO clip 保证策略更新稳定
- 多 epoch 更新（默认 4 个 epoch）
- 梯度裁剪

**超参数默认值**：

| 参数 | 默认值 |
|------|--------|
| 隐藏层维度 | 128 |
| Actor 学习率 | 3e-4 |
| Critic 学习率 | 1e-3 |
| 折扣因子 γ | 0.99 |
| GAE λ | 0.95 |
| PPO clip ε | 0.2 |
| 熵系数 | 0.01 |
| 价值系数 | 0.5 |
| 最大梯度范数 | 0.5 |
| 更新间隔 | 300 步 |
| batch_size | 64 |

**模型保存/加载**：
- 支持保存策略网络和价值网络参数
- 支持加载预训练模型

#### 5.3.6 SCOOT 降级控制器需求

**功能要求**：
- 当 MAPPO 不可用时，使用 SCOOT-like 自适应控制
- 实时检测各相位的车辆需求
- 根据饱和度动态调整周期长度
- 基于压力均衡原则分配绿信比

**决策规则**：

| 规则 | 条件 | 动作 |
|------|------|------|
| 规则1 | 当前相位时间 < 最小绿灯 | 保持 (keep) |
| 规则2 | 当前相位时间 ≥ 最大绿灯或分配绿灯 | 切换 (switch) |
| 规则3 | 当前相位排队清除且其他相位需求高 | 切换 (switch) |
| 规则4 | 当前相位需求仍然高且未到最大绿灯 | 延长 (extend) |
| 默认 | - | 保持 (keep) |

**周期自适应调整**：
- 每 300 步检查一次
- 过饱和（饱和度 > 0.8）→ 增大周期 10%
- 低饱和（饱和度 < 0.3）→ 减小周期 10%
- 正常 → 保持

**绿信比分发**：
- 基于各相位需求比例分配有效绿灯时间
- 保证每相位不小于最小绿灯
- 需求极低时均匀分配

**默认参数**：

| 参数 | 默认值 |
|------|--------|
| 最小周期 | 40s |
| 最大周期 | 180s |
| 最小绿灯 | 8s |
| 最大绿灯 | 60s |
| 黄灯时间 | 3s |
| 全红时间 | 2s |
| 延长绿灯需求阈值 | 0.3 |
| 切换相位需求阈值 | 0.15 |
| 周期调整间隔 | 300 步 |

#### 5.3.7 方案二控制器需求

**初始化**：
- 初始化状态编码器（构建观测空间、邻居图）
- 初始化奖励计算器（注入邻居关系）
- 初始化 STGCN 预测器（尝试加载模型）
- 初始化 MAPPO 策略网络（尝试加载模型）
- 初始化 SCOOT 降级控制器
- 确定运行模式（auto/mappo/scoot）

**运行模式**：

| 模式 | 说明 |
|------|------|
| auto | 自动选择：有模型用 MAPPO，否则用 SCOOT |
| mappo | 强制使用 MAPPO（需要框架支持） |
| scoot | 强制使用 SCOOT |

**每步逻辑**：
- 每 10 步更新一次交通流预测
- 每 5 步做一次决策（采集观测 → 选择动作 → 应用动作 → 计算奖励）
- MAPPO 训练模式下定期更新策略

**决策流程**：
1. 采集所有交叉口的观测
2. 计算全局指标
3. 为每个交叉口选择动作（MAPPO 或 SCOOT）
4. 应用动作到仿真引擎（切换相位或延长绿灯）
5. 计算奖励
6. 训练模式下存储经验

**支持的 API 动作**：

| 动作 | 说明 |
|------|------|
| switch_to_mappo | 切换到 MAPPO 模式 |
| switch_to_scoot | 切换到 SCOOT 模式 |
| switch_to_auto | 自动模式选择 |
| train_step | 手动触发一次策略更新 |
| save_model | 保存模型 |
| load_model | 加载模型 |
| set_params | 设置参数（决策间隔、绿灯范围等） |
| get_predictions | 获取交通流预测结果 |
| get_status | 查询算法状态 |

**状态查询需返回**：
- 当前运行模式
- MAPPO 状态（模式、框架可用性、模型加载状态、观测维度、动作数、经验数、更新次数、奖励统计、超参数）
- STGCN 状态（模式、模型加载状态、edge 数、历史长度、更新次数、预测次数）
- SCOOT 状态（活跃交叉口数、切换/延长/周期调整次数、各交叉口状态）
- 状态编码器信息（观测维度、TLS 数、邻居边数）
- 奖励统计（切换统计）
- 决策统计（决策次数、MAPPO 动作数、SCOOT 动作数、降级次数）

### 5.4 方案三：受限车队路线引导（动态 Dijkstra + 负载均衡）

#### 5.4.1 功能概述

对公交、网约车等车队车辆提供动态路线引导，基于实时路况为车队车辆重新规划最优路线，支持负载均衡和受限区域。包含四个子模块：

1. **路网图**：从仿真引擎构建路网图结构
2. **边权重管理器**：采集和计算路网中每条 edge 的实时权重
3. **车队管理器**：识别、注册和跟踪车队车辆
4. **路线规划器**：动态 Dijkstra + K-短路 + 负载均衡

#### 5.4.2 路网图需求

**功能要求**：
- 从仿真引擎获取所有 edge 和 node 信息，构建有向图
- 每个 edge 记录：edge_id、起止节点、长度、限速、车道数、道路类型、是否允许通行
- 每个 node 记录：node_id、坐标、关联信号灯、入边列表、出边列表
- 支持添加/移除受限 edge（标记为不允许通行）
- 支持路线连续性验证
- 计算自由流旅行时间 = 长度 / 限速

#### 5.4.3 边权重管理器需求

**权重计算流程**：

```
base_travel_time = max(SUMO旅行时间, edge长度/平均速度)
smoothed_travel_time = α × base_travel_time + (1-α) × 上次平滑值    # α=0.3
final_weight = smoothed_travel_time + load_penalty
```

**负载惩罚**：
- 每分配一辆车队车辆到某 edge，增加惩罚（默认 2s/辆）
- 最大负载惩罚上限（默认 60s）

**拥堵判定**：
- 占有率 > 0.7 视为拥堵
- 拥堵级别 = 占有率

**功能要求**：
- 初始化时从路网图获取所有 edge 的基础属性
- 每 5 步更新一次所有 edge 的实时权重
- 限制采样量（默认最多 500 条 edge）以提高性能
- 支持 EWMA 平滑避免权重跳变
- 支持增加/减少/清除 edge 负载
- 支持查询拥堵 edge 列表
- 支持查询拥堵最严重的 N 条 edge
- 支持参数动态调整

**通行能力估算**：
```
capacity = lanes × speed_limit × 0.4 × 3600 / (vehicle_length + spacing)
```
默认车辆长度 5m，间距 2m。

#### 5.4.4 车队管理器需求

**车队类别**：

| 类别 | 说明 | 自动识别规则 |
|------|------|-------------|
| bus | 公交车 | ID 前缀 bus/route，车辆类型 bus/coach |
| ride_hail | 网约车 | ID 前缀 fleet/ride |
| delivery | 配送车 | ID 前缀 deliver，车辆类型 truck/trailer |
| emergency | 应急车辆 | ID 前缀 emergency/ambulance，车辆类型 emergency |
| custom | 自定义车队 | 仅手动注册 |

**功能要求**：
- 自动扫描路网中的车辆，基于 ID 前缀和车辆类型识别车队车辆
- 支持手动注册/注销车队车辆
- 跟踪每辆车的当前路线、目的地、当前位置
- 记录路由历史（重路由次数、原始路线、路线历史、预估节省时间）
- 管理重路由冷却时间（防止频繁重路由，默认 60 步）
- 处理车辆进出路网事件
- 自动清理已到达的非手动注册车辆
- 支持按类别查询车辆

**车队车辆数据结构**：
- 车辆 ID、类别
- 当前路线（edge ID 列表）、目的地 edge、起点 edge、当前 edge
- 重路由次数、原始路线、路线历史
- 出发步数、预估到达步数、预估节省时间
- 是否启用自动重路由、最后重路由步数
- 是否在路网中、是否已到达

#### 5.4.5 路线规划器需求

**核心算法**：
1. **Dijkstra 最短路径**：基于实时边权重计算最短路径
2. **K-短路**：计算前 K 条候选路线（简化版 Yen's algorithm）
3. **负载均衡**：同一 OD 对分配多辆车时分散到不同路线

**Dijkstra 需求**：
- 基于 edge 权重（旅行时间）计算最短路径
- 支持避开指定 edge（avoid_edges）
- 跳过受限 edge（不允许通行的 edge）
- 最大路线长度限制（默认 100 个 edge）
- 路径回溯后确保以起点 edge 开头、终点 edge 结尾

**K-短路需求**：
- 先计算最短路径
- 逐个移除最短路径中的 edge，重新计算得到备选路线
- 去重后按权重排序取前 K 条
- 默认 K=3

**负载均衡需求**：
- 记录每个 OD 对已分配的路线
- 分配数低于阈值（默认 3）时直接选最短路径
- 超过阈值时选择已分配车辆最少的路线
- 路线重叠率用 Jaccard 相似度计算

**路线应用**：
- 验证路线连续性
- 连续时设置车辆路线到仿真引擎
- 不连续时回退到仿真引擎的自动重路由

**批量重路由**：
- 接收多辆车的 OD 信息
- 逐辆规划并应用路线
- 返回每辆车的规划结果

**路线推荐**：
- 接收起点和终点 edge
- 返回 K 条候选路线（含总权重、总长度、预估时间、edge 数量、是否包含受限 edge、规划方法）

#### 5.4.6 方案三控制器需求

**初始化**：
- 从仿真引擎构建路网图
- 初始化边权重管理器
- 初始化车队管理器（启用自动识别）
- 初始化路线规划器
- 加载受限区域配置（如有）

**每步逻辑**：
- 每 5 步更新一次边权重
- 每 10 步扫描一次车队车辆
- 每步处理车辆进出路网事件
- 每 10 步更新车队车辆位置（移动时更新 edge 负载）
- 每 30 步检查一次自动重路由（找出拥堵 edge 上的车队车辆，重新规划路线）

**自动重路由流程**：
1. 获取所有拥堵 edge 列表
2. 找出处于拥堵 edge 上的车队车辆（且冷却期已过）
3. 限制每轮重路由数量（默认 20 辆）
4. 为每辆车规划新路线（负载均衡）
5. 应用路线到仿真引擎
6. 记录重路由事件和节省时间
7. 推送事件到前端

**支持的 API 动作**：

| 动作 | 说明 | 参数 |
|------|------|------|
| reroute_fleet | 手动重路由指定车队 | vehicle_ids, destinations |
| register_fleet | 注册车队车辆 | vehicle_ids, category, destinations |
| unregister_fleet | 注销车队车辆 | vehicle_ids |
| add_restricted_zone | 添加受限区域 | edge_ids, reason |
| remove_restricted_zone | 移除受限区域 | edge_ids |
| clear_restricted_zones | 清除所有受限区域 | - |
| enable_auto_reroute | 启用/禁用自动重路由 | enabled, vehicle_ids(可选) |
| set_params | 设置参数 | scan_interval, reroute_interval, load_penalty_per_vehicle 等 |
| get_fleet_status | 查询车队状态 | detail, limit |
| get_route_recommendations | 获取路线推荐 | from_edge, to_edge, k |
| get_congestion_map | 获取拥堵地图 | - |
| get_status | 查询算法状态 | - |

**状态查询需返回**：
- 路网图信息（节点数、边数、受限边数）
- 边权重管理器状态（edge 数、更新次数、拥堵 edge 数、总负载、参数）
- 车队管理器状态（注册总数、活跃数、重路由数、到达数、各类别数量、参数）
- 路线规划器状态（规划总数、重路由数、失败数、负载均衡数、活跃分配数、OD 对数、参数）
- 自动重路由开关状态
- 统计信息（总重路由数、自动/手动重路由数、受限区域增减数）
- 配置参数

## 6. 可视化需求

### 6.1 路网渲染

- 从后端获取 GeoJSON networks
- 将每条 edge 渲染为线段，颜色按道路类型区分
- 渲染交叉口节点
- 支持缩放、平移、旋转
- 路网需在仿真启动前加载显示

### 6.2 车辆渲染

- 接收实时推送的车辆增量更新（added/updated/removed）
- 使用高性能渲染方式（如实例化渲染）支持数千辆车同时显示
- 车辆按类型着色：

| 车辆类型 | 颜色 |
|----------|------|
| 小客车 passenger | 蓝色 |
| 公交 bus | 红色 |
| 车队 fleet | 橙色 |
| 货车 truck | 紫色 |
| 自行车 bicycle | 绿色 |

- 车辆位置实时更新，朝向与角度一致
- 支持视域裁剪：只渲染视域范围内的车辆

### 6.3 信号灯渲染

- 在交叉口位置渲染信号灯状态指示器
- 颜色与信号灯状态字符串对应（绿灯/红灯/黄灯）
- 状态变化时实时更新

### 6.4 控制面板

**仿真控制**：
- 启动/暂停/恢复/停止按钮
- 速度倍率调节（滑块或输入框，范围 0-100）
- 手动步进按钮
- 仿真状态显示（当前步数、仿真时间、车辆数、速度）
- WebSocket 连接状态指示

**方案管理**：
- 方案选择下拉框（scheme_1/scheme_2/scheme_3/none）
- 方案状态显示
- 方案特定操作按钮（按选中方案动态显示）

**方案一操作**：
- TOD 时段切换（下拉选择 + 切换按钮）
- 解除强制时段按钮
- 手动重算按钮
- 绿波协调开关
- 走廊信息展示

**方案二操作**：
- 模式切换（MAPPO/SCOOT/Auto）

- 模型保存/加载
- 参数设置
- 预测结果查看

**方案三操作**：
- 车队注册/注销

- 路线推荐查询
- 拥堵地图查看

### 6.5 指标展示

**全局指标面板**：
- 实时显示车辆数、平均速度、平均延误、通过量、排队长度、等待时间

**指标图表**：
- 折线图展示历史指标趋势（平均延误、平均速度、通过量、排队长度）

## 8. 非功能性需求

### 8.1 性能需求

| 需求 | 指标 |
|------|------|
| 车辆渲染 | 支持同时渲染 3000+ 辆车，帧率不低于 30fps |
| 实时推送延迟 | 车辆位置更新延迟不超过 1 秒 |
| API 响应时间 | 常规 API 响应时间不超过 200ms |
| 仿真步进 | 1 倍速下每步不超过 1 秒实际时间 |
| 边权重更新 | 500 条 edge 的权重更新不超过 2 秒 |
| 路线规划 | 单次 Dijkstra 计算不超过 100ms |

### 8.2 可靠性需求

- 仿真引擎连接断开时，系统需优雅降级而非崩溃
- WebSocket 断开后支持自动重连
- 算法异常时需捕获并推送错误事件，不影响仿真继续运行
- 方案二在模型不可用时需自动降级到 SCOOT

### 8.3 可扩展性需求

- 调度算法采用插件式架构，新增方案只需实现基类接口
- networks支持不同区域，不限于雄安
- 方案配置支持运行时动态调整，无需重启仿真
- 前端支持多客户端同时连接

### 8.4 可维护性需求

- 前后端接口需有完整文档，包含请求/响应格式、字段说明
- 数据格式需有规范文档，描述所有数据结构
- 代码需有注释，关键算法需有公式说明
- 各模块间通过明确接口耦合，避免直接访问内部状态

### 8.5 安全性需求

- API 需有错误码体系，不泄露内部异常堆栈
- WebSocket 消息需有格式校验，非法消息返回错误而非崩溃
- 文件路径参数需做安全校验，防止路径遍历
