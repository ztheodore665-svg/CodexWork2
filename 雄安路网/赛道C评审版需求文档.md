# XH-202613 赛道 C 评审版需求文档
## 雄安城市大脑车路云一体化协同管控算法与仿真平台

> 版本：v1.0（评审提交稿）  
> 赛道：赛道 C - AI 应用型  
> 项目定位：面向雄安新区窄路密网交通场景的 AI 驱动、可部署、可复现的车路云协同管控平台

---

## 1. 项目摘要

本项目面向雄安新区“窄路密网”交通环境，建设一套以 SUMO 微观交通仿真为验证底座、以多智能体强化学习和时空交通预测为核心、以车路云协同为组织方式的交通管控算法与仿真平台。

平台围绕赛道 C 对 AI 应用型项目的核心要求，形成完整的：

```text
交通场景构建
    -> AI 模型开发与训练
    -> 模型选择与验证
    -> 模型转换与轻量化部署
    -> 云边协同交通控制
    -> 仿真评测与结果报告
```

项目解决的不是“能否调用一个 AI 模型”的问题，而是将 AI 模型放入真实约束下的交通控制闭环：模型根据交通状态进行预测和决策，边缘控制器将决策转化为安全信号动作，车辆侧执行动态路径引导，系统再通过仿真状态和量化指标验证效果。

## 2. 需求背景与建设目标

### 2.1 场景问题

雄安容东片区道路密度高、交叉口间距小、局部道路容量有限，交通拥堵具有明显的时空传播特征。传统固定配时能够满足低负荷条件下的基本通行，但面对高峰、区域热点、施工占道和大型活动等扰动时，往往难以及时感知和协同响应。

平台需要回答三个问题：

1. 能否在雄安真实路网结构上感知和预测交通状态？
2. AI 是否能够在信号控制、区域协调和路径引导中产生可量化收益？
3. AI 模型能否经过转换和部署，进入一个可运行、可解释、可降级的交通管控系统？

### 2.2 建设目标

| 目标 | 目标说明 |
|---|---|
| AI 应用落地 | 将 STGCN 交通预测、MAPPO 多路口控制和动态路径规划用于可验证的交通管控任务 |
| 模型工程闭环 | 覆盖模型开发、训练/选择、验证、ONNX 转换、CPU 推理和平台部署 |
| 车路云协同 | 形成 Cloud 全局协调、Edge/RSU 路口控制、Vehicle 路径执行的分层闭环 |
| 场景真实性 | 使用雄安目标路网、交通需求、信号配时和可配置扰动开展评测 |
| 结果可信 | 采用同路网、同车流、同事件、固定种子和多指标评测，避免只展示单次最好结果 |
| 工程可用 | 具备模型异常、通信受限和控制超时情况下的安全降级能力 |

## 3. 产品定位与评审表达

### 3.1 产品定位

**雄安城市大脑车路云一体化协同管控算法与仿真平台**是一套面向城市交通 AI 应用验证的数字靶场与智能控制平台。

它同时具备三种属性：

- **算法验证平台**：支持 AI 模型训练、验证、对比和部署；
- **交通控制系统原型**：具备信号控制、路径引导、事件响应和降级策略；
- **标准化评测工具**：支持固定场景、批量实验、指标统计和报告生成。

### 3.2 项目优势

1. **问题聚焦**：围绕雄安窄路密网这一具体交通问题展开，不做泛化的 AI 展示。
2. **模型有任务**：STGCN 用于短时交通状态预测，MAPPO 用于多路口协同信号控制，Dijkstra/K 短路用于车辆路径执行，各模型职责清晰。
3. **模型可部署**：支持 PyTorch 模型验证、ONNX/INT8 转换和 CPU 推理，展示从模型到应用的完整链条。
4. **系统可闭环**：AI 输出不是孤立结果，而是进入 Edge 控制、Vehicle 执行，并通过 KPI 和实验报告回收效果。
5. **工程有护栏**：模型缺失、推理异常、通信超时或控制动作非法时，系统可回退到 SCOOT 或 Fixed-Time。
6. **结果可复现**：同一配置下复用车流、事件序列和随机种子，保留原始数据、模型版本和运行日志。

## 4. 用户角色与使用目标

| 用户 | 使用目标 | 关注结果 |
|---|---|---|
| 交通管理人员 | 观察路网、注入事件、调整策略 | 拥堵是否缓解，重点区域是否恢复 |
| 算法研发人员 | 训练、选择、接入和验证模型 | 模型效果、推理延迟、泛化和稳定性 |
| 评测人员 | 批量运行统一实验 | 不同方案的公平比较和可复现数据 |
| 评委/观众 | 快速理解项目价值 | AI 是否真正改变了交通控制结果 |

## 6. 赛道 C AI 应用需求

### 6.1 AI 应用任务一：短时交通状态预测

系统应根据路段流量、速度、占有率、排队等历史时序数据，预测未来短时间窗口内的交通状态，为区域协调和信号控制提供先验信息。

**输入**：路段/路口历史状态、时间窗口、场景和事件信息。  
**输出**：未来路段流量、速度或拥堵趋势。  
**使用方式**：预测结果进入 Cloud 层，用于识别拥堵传播方向和调度区域。

### 6.2 AI 应用任务二：多路口协同信号控制

MAPPO 将多个信号路口作为协同智能体，根据本地队列、相位、速度和邻接路口状态输出控制动作。控制动作遵守交通信号安全约束，并支持 SCOOT/Fixed-Time 降级。

**输入**：路口观测、相邻路口状态、预测交通状态和当前相位。  
**输出**：保持或推进相位等控制动作。  
**约束**：最小绿、最大绿、黄灯、全红、相位过渡和防止方向长期饥饿。

### 6.3 AI 应用任务三：交通事件下的协同决策

在大型活动、施工占道、道路封闭和突发事故等场景下，系统应完成“事件识别/注入 - 状态分析 - 预测 - 控制 - 路由 - 反馈”闭环。

事件可以由前端、API 或 LLM Agent 注入；AI 负责提供预测和控制建议，最终执行由带安全校验的控制器完成。

### 6.4 AI 应用任务四：车辆路径引导

车辆侧基于实时旅行时间、道路容量、限制区域和车辆任务约束计算路径。对普通车辆、公交、配送车和应急车辆可配置不同的路径代价和优先级。

## 7. AI 模型全生命周期需求

### 7.1 模型开发

- 模型应有明确任务、输入、输出、训练数据和评价指标；
- 训练配置、观测维度、动作空间和场景范围必须版本化；
- 模型训练与平台推理使用一致的特征归一化和动作语义；
- 模型不得仅以网络结构名称作为创新说明，应说明其对交通问题的作用。

### 7.2 训练与模型选择

模型选择应至少结合：

- 交通效率：平均延误、速度、吞吐、排队；
- 稳定性：不同 seed、不同负荷和不同事件下的波动；
- 公平性：平均等待与长尾等待；
- 工程性：推理耗时、模型体积和资源占用；
- 安全性：非法动作、冲突相位和异常降级次数。

### 7.3 模型验证

验证不得只使用训练场景的单次结果。最低验证矩阵为：

| 维度 | 建议设置 |
|---|---|
| 场景 | 正常高峰、区域热点、大型活动+施工、应急保障 |
| 负荷 | 80%、100%、120% 或等价三档 |
| 对照 | Fixed-Time、SCOOT、MAPPO、Proposed |
| 随机性 | 至少 5 个固定 seed，每个 seed 一次独立运行 |
| 指标 | 延误、速度、吞吐、排队、等待、完成率、推理延迟 |

### 7.4 模型转换与部署

平台应展示以下可追溯链路：

```text
PyTorch 训练模型
      -> 验证模型
      -> ONNX FP32
      -> ONNX INT8（可选）
      -> ONNX Runtime CPU 推理
      -> Edge/平台控制器部署
```

转换后应核验：

- 输入输出维度一致；
- 关键样本输出误差在约定范围内；
- 动作选择一致率满足验收要求；
- 推理延迟满足控制周期；
- 模型文件、转换脚本和验证结果可交付。

### 7.5 模型异常与安全降级

| 异常 | 处理 |
|---|---|
| 权重不存在或版本不匹配 | 切换 SCOOT 或 Fixed-Time |
| 推理超时 | 保持安全相位；连续超时触发降级 |
| 输出维度/数值非法 | 丢弃动作并记录 |
| Cloud 预测不可用 | Edge 继续使用本地观测 |
| V2X 延迟/丢包 | 使用最近有效策略并限制有效期 |
| 控制动作冲突 | 安全校验拒绝，不执行非法动作 |

## 8. 功能需求

### 8.1 雄安交通数字场景

- 支持雄安目标路网加载，目标场景包含 20 个以上可控路口；
- 支持道路、车道、路口、信号灯、车辆和交通需求配置；
- 支持正常高峰、区域热点、过饱和和应急保障场景；
- 支持同车流文件复用，保证不同算法公平对比；
- 支持路网和场景摘要、GeoJSON 导出及版本记录。

### 8.2 事件中心

至少支持施工占道、道路封闭、大型活动、事故、突发车流和通信异常。事件具备唯一 ID、作用对象、开始/结束时间、影响参数、状态和审计记录。

### 8.3 算法与方案管理

系统应提供统一算法列表、版本、能力、模型状态、参数和运行状态。至少支持：

- Fixed-Time 基线；
- Webster + MAXBAND；
- SCOOT-like 自适应控制；
- MAPPO + STGCN；
- Proposed Cloud-Edge-Vehicle；
- 动态路径引导。

### 8.4 可视化驾驶舱

- 展示路网、车辆、信号灯、拥堵热区和事件；
- 展示 Cloud、Edge、Vehicle 当前状态；
- 展示 AI 预测趋势、控制动作和路径变化；
- 展示延误、速度、吞吐、排队、等待和完成率；
- 支持 Baseline vs Proposed 同场景对比；
- 支持自然语言查询、事件注入、策略切换和报告生成。

### 8.5 Benchmark 与报告

Benchmark 应支持配置场景、交通负荷、算法、seed、通信条件、仿真时长和 warmup，批量执行并输出：

- 原始结果 CSV/JSON；
- 均值、标准差、P50/P95；
- 相对基线改善率；
- 模型和代码版本；
- 失败、超时和降级运行记录；
- 图表和结论摘要。

## 9. 评测指标与验收口径

### 9.1 指标体系

| 维度 | 指标 |
|---|---|
| 通行效率 | 平均延误、平均旅行时间、平均速度、吞吐量 |
| 拥堵状态 | 平均/最大排队、平均/P95 等待、完成率 |
| 环境效果 | 油耗、CO₂ 排放（以 SUMO 可获得指标为准） |
| 安全性 | 非法动作、冲突相位、急刹车或 TTC 等可选指标 |
| 工程部署 | 模型体积、CPU 推理延迟、API 延迟、降级次数 |

### 9.2 评测原则

- 不用单一指标替代整体结论；
- 不将低负荷“都不堵”或超饱和“都堵死”作为唯一主实验；
- 所有算法使用同一份路网、车流、事件和随机 seed；
- warmup 默认 90 秒，采样间隔默认 30 秒；
- 报告均值、标准差和长尾指标，不只报告最佳运行；
- 评测结果说明适用的仿真条件，不作真实道路部署承诺。

### 9.3 评审可观察的验收结果

1. 雄安 20+ 路口场景连续运行 600 个仿真秒，无崩溃和非预期断连；
2. AI 模型能够完成一次从加载、推理、控制到指标反馈的完整闭环；
3. ONNX 模型能够在 CPU 环境完成推理并记录延迟；
4. 注入大型活动+施工占道后，系统能够展示预测、信号控制、路径引导和 KPI 变化；
5. 模型不可用或超时时，系统在 2 个控制周期内降级且不产生冲突相位；
6. 至少完成 4 类场景、3 档负荷、4 类算法、5 个 seed 的 Benchmark 配置和结果导出；
7. 标准演示流程连续执行 3 次无阻断性错误。

## 10. 典型演示流程

### 10.1 推荐主演示：大型活动散场 + 施工占道

```text
1. 加载雄安 20+ 路口路网
2. 运行 Fixed-Time 基线并显示初始 KPI
3. 注入大型活动散场交通流
4. 注入局部施工占道
5. 展示拥堵形成和 STGCN 趋势预测

8. Vehicle 执行动态路径引导
9. 展示 Proposed 与 Baseline 的 AB 对比
10. 展示延误、排队、速度、吞吐和完成率变化
11. 打开模型部署信息和实验报告
```

### 10.2 演示表达重点

建议评委看到的重点顺序是：

1. 这是雄安具体交通问题；
2. AI 模型有明确任务，不是泛化聊天或单点预测；
3. 模型经过验证、转换并真正进入控制链路；
4. AI 输出受到交通安全规则和传统算法保护；
5. 最终效果能够通过同条件对比和量化指标复核。

## 12. 风险与边界说明

### 12.1 评测边界

本平台用于交通控制方案的仿真验证和 AI 应用展示。仿真结果受路网、交通需求、SUMO 参数、模型训练范围和评价指标影响，不直接等价于真实道路收益。

### 12.2 数据边界

平台中的合成交通需求、校准数据和仿真数据在报告中分别标注，不将仿真生成数据表述为实时真实交通数据。

### 12.3 工程边界

当前阶段重点验证算法闭环、模型部署和车路云协同逻辑；真实信号机、RSU、车端硬件和生产级多用户安全体系属于后续工程化方向，不作为本次赛道 C 核心验收前提。

## 13. 项目结论

本项目以雄安窄路密网交通问题为牵引，将 AI 模型开发、训练/选择、模型转换、边缘部署、交通控制和量化评测组织为一个完整应用闭环。

项目的核心竞争力不是算法名称的堆叠，而是：

> **AI 模型有明确交通任务，模型能够进入车路云控制链路，系统具备安全降级，效果能够在统一场景下复现和比较。**

这使平台既能满足赛道 C 对 AI 应用型项目的要求，也能以可运行、可解释、可验证的方式向评委展示其工程价值和推广潜力。
