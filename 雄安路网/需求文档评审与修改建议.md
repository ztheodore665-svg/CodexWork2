# 《雄安城市大脑车路云协同交通管控平台需求文档初稿》评审与修改建议

> 评审对象：`雄安路网/需求文档初稿.md`  
> 评审版本：v0.1（评审稿）  
> 对应提交：`9d8d8c8`  
> 评审日期：2026-09-08  
> 评审目的：判断文档是否能够作为产品规划、开发拆分、实验评测和项目验收的统一依据，并提出 v0.2 修订建议。

## 1. 总体评价

该文档框架完整、方向正确，已经能够用于团队统一项目认识和开展第一轮需求评审。文档将项目定位为覆盖“场景生成—事件注入—状态感知—协同决策—执行反馈—指标评测—报告生成”的车路云协同闭环，而非单纯的 SUMO 仿真播放器或算法演示，定位具有较好的工程价值和比赛表达力。

当前文档仍同时包含产品需求、技术方案、现状评估、研发计划和验收设想，部分需求缺少量化判定条件。因此，它目前更适合作为“需求与方案综合初稿”，尚不能直接作为开发任务拆分和正式验收的唯一依据。

综合评价如下：

| 使用场景 | 评价 | 说明 |
|---|---:|---|
| 比赛项目需求初稿 | 8/10 | 定位清晰、覆盖全面、重点判断合理 |
| 开发需求基线 | 6.5/10 | 关键方案边界、接口契约和范围仍需明确 |
| 正式验收依据 | 5.5/10 | 多项标准缺少测试条件、量化阈值和计算口径 |

建议先完成 Proposed 方案定义、P0 验收量化、Benchmark 统计口径、范围边界和需求追踪五项修订，再将文档升级为 v0.2 需求基线。

## 2. 文档的主要优点

### 2.1 产品定位清晰

文档没有把项目局限为交通仿真或单一算法 Demo，而是明确提出完整闭环平台，并将数字靶场、云边端协同、算法对比、可复现实验和报告交付统一组织起来。这一定位既方便指导建设，也便于赛事答辩时说明项目价值。

### 2.2 正确识别了当前建设重点

文档将以下事项列为 P0：

- Fixed-Time 统一基线；
- 扰动事件中心；
- Cloud-Edge-Vehicle 协同模型；
- Benchmark 执行器；
- 20 个以上路口稳定运行；
- 可复现实验和安全降级。

这一优先级判断较为合理。现阶段项目的关键不是继续增加算法数量，而是将已有算法组织成稳定、可比较、可复现、可演示的产品闭环。

### 2.3 功能覆盖较完整

场景工厂、事件中心、仿真会话、算法管理、云边端协同、V2X、可视化驾驶舱、LLM Agent、Benchmark 和报告输出均有涉及。文档也开始采用 `SCN-001` 等编号，为后续建立需求追踪关系提供了基础。

### 2.4 重视可复现性和安全降级

文档要求固定随机种子、保存原始结果、绑定代码和模型版本，并在模型缺失、推理异常或通信失败时安全降级。这些内容具有实际工程价值，也有利于提高比赛成果的可信度。

## 3. 优先修改的问题

### 3.1 P0：验收标准缺少量化条件

#### 问题说明

文档中的部分验收表述仍然依赖主观判断，例如：

- “20+ 路口场景能够稳定运行”；
- “同配置重复运行结果在允许误差范围内一致”；
- “算法决策不得阻塞 API 和 WebSocket 服务”；
- “维持基本交通服务”；
- “完成 5–8 分钟稳定演示流程”。

这些表述指出了目标，但测试人员无法仅根据文档判断通过或失败。

#### 修改建议

每项验收标准应至少包含：前置条件、测试输入、执行步骤、预期结果、量化阈值和证据形式。

建议将相关要求改写为：

| 验收方向 | 建议判定标准 |
|---|---|
| 仿真稳定性 | 目标路网连续运行不少于 600 个仿真秒；无进程崩溃、无 TraCI 非预期断连、无未处理异常；会话停止后资源正常释放 |
| 接口性能 | 在规定测试环境和车辆规模下，普通查询接口 P95 响应时间不超过 200 ms；控制接口另行规定阈值 |
| 算法耗时 | 单次控制决策 P95 耗时不超过控制周期的 80%，超时自动触发预定降级策略 |
| 可复现性 | 相同路网、车流文件、事件序列、算法版本和种子下，离散输入完全一致；核心统计指标相对误差不超过约定阈值 |
| 降级安全性 | 故障被检测后在规定仿真步数内完成降级；不得产生冲突相位；最小绿、最大绿、黄灯和全红约束保持有效 |
| 演示稳定性 | 标准演示连续执行完整流程不少于 3 次，无阻断性错误，页面核心指标和动作链路均可展示 |

具体数值应结合现有代码性能和比赛环境校准，正式基线中不能继续使用“适当”“稳定”“允许误差”等未定义词语。

### 3.2 P0：Proposed 协同方案定义不明确

#### 问题说明

文档要求比较 `MAPPO + STGCN` 和 `Proposed Cloud-Edge-Vehicle`，但没有明确 Proposed 的算法组成、输入输出、控制周期和决策权限。因此存在以下风险：

- Proposed 与 `MAPPO + STGCN` 能力重叠；
- 是否包含动态路径引导不明确；
- Cloud 与 Edge 谁拥有最终信号控制权不明确；
- 不同方案启用的能力不同，实验结果无法公平归因；
- 无法判断 Proposed 是否已经实现以及何时验收完成。

#### 修改建议

增加独立章节《Proposed 方案定义》，至少说明：

1. Cloud、Edge、Vehicle 分别使用的算法或规则；
2. 三层之间交换的消息；
3. 每类决策的周期、时限和有效期；
4. 最终信号动作与路径动作的决策权；
5. 异常、冲突和通信超时时的处理顺序；
6. 相对基线新增的唯一能力。

同时增加方案能力矩阵：

| 方案 | 交通预测 | 信号控制 | 路径引导 | 云端协调 | 安全降级 |
|---|---|---|---|---|---|
| Fixed-Time | 无 | 固定配时 | 无 | 无 | 固定配时 |
| Webster + MAXBAND | 可选 | 周期与绿信比优化 | 无 | 走廊协调 | Fixed-Time |
| SCOOT-like | 无或可选 | 本地自适应 | 无 | 可选 | Fixed-Time |
| MAPPO + STGCN | STGCN | MAPPO | 待定义 | 待定义 | SCOOT/Fixed-Time |
| Proposed | 待明确 | 待明确 | 待明确 | 待明确 | 待明确 |

最终文档应将所有“待明确”替换为可实现、可测试的具体定义。

### 3.3 P0：Benchmark 重复实验和统计口径存在歧义

#### 问题说明

示例配置同时使用：

```json
{
  "seeds": [42, 43, 44, 45, 46],
  "repetitions": 5
}
```

目前无法判断是每个种子运行一次、每个种子重复五次，还是五次运行分别使用五个种子。如果同一种子下仿真完全确定，对同一个种子重复运行通常不会产生新的统计信息。

文档也尚未明确：

- P95 是对车辆样本、时间序列还是多次实验结果计算；
- 标准差是跨车辆、跨时间窗口还是跨随机种子计算；
- “提升比例”的分母和方向；
- 失败或降级运行是否纳入汇总；
- 是否使用置信区间或显著性检验；
- 不同算法是否使用同一份预生成车流和事件序列。

#### 修改建议

建议将每个种子定义为一次独立重复实验，例如：

```json
{
  "seeds": [42, 43, 44, 45, 46],
  "runs_per_seed": 1
}
```

如确需同种子重复，则应说明非确定性来源，并明确总运行次数为：

```text
总运行次数 = 场景数 × 负荷档位数 × 通信条件数 × 算法数 × 种子数 × 每种子重复次数
```

建议在文档中统一定义：

- 单次运行指标的采样窗口；
- 车辆级、时间级和运行级聚合顺序；
- 均值、标准差、P50、P95 的样本集合；
- 改善率计算公式；
- 95% 置信区间或选定的显著性检验方法；
- 异常、超时、降级和无效运行的处理规则。

### 3.4 P0：缺少明确的范围与非目标

#### 问题说明

当前文档同时覆盖 20+ 路口、八类事件、六类算法方案、V2X、LLM Agent、AB 同屏、安全指标、自动报告和标准规程，范围较大。若不划定边界，容易造成比赛阶段任务持续扩张。

#### 修改建议

增加《范围与非目标》章节，至少确认：

- 本期必须交付、可选交付和明确不交付的能力；
- 项目属于比赛演示级、科研原型级还是生产系统级；
- 是否接入真实 RSU、车端硬件和实时交通数据；
- 是否支持多个用户和多个并发仿真任务；
- 是否提供互联网公开访问；
- 是否需要完整账号和权限系统；
- 仿真结论是否仅用于方案对比，而不直接代表真实道路部署效果。

建议明确声明：当前阶段的评测结论基于指定路网、交通需求、模型参数和 SUMO 仿真条件，不直接构成真实道路部署效果承诺。

### 3.5 P1：需求、设计、现状评估和研发计划混合

#### 问题说明

文档中同时出现 FastAPI、Vue 3、Canvas、算法生命周期接口、容器部署方式、项目完善性评估和开发优先级。这些内容分别属于产品需求、技术设计、现状分析和研发计划。

#### 修改建议

条件允许时拆分为：

1. 《产品需求规格说明书》；
2. 《系统架构与接口设计》；
3. 《Benchmark 与验收测试规程》；
4. 《项目现状差距与迭代计划》；
5. 《赛事演示与交付说明》。

若比赛周期内暂不拆分文件，应为每个条目标注类别：

- `BR`：业务需求；
- `FR`：功能需求；
- `NFR`：非功能需求；
- `TC`：技术约束；
- `DS`：设计建议；
- `AC`：验收规则。

## 4. 建议补充的关键需求

### 4.1 时间语义

统一说明以下时间的含义、单位和转换关系：

- 仿真时间；
- 系统时间；
- 消息生成时间和到达时间；
- 事件开始、结束和撤销时间；
- 算法决策生效时间与失效时间。

暂停、调速、单步和恢复时，事件及 V2X 消息应以仿真时间推进，避免依赖真实时间造成不可复现。

### 4.2 标识、坐标和单位

补充以下约定：

- 路网、道路、车道、路口、信号灯、车辆和事件的唯一标识规则；
- SUMO ID 与平台业务 ID 的映射关系；
- GeoJSON 坐标系和地图投影；
- 速度、距离、时间、排放量等字段单位；
- 浮点数精度和缺失值表达方式。

### 4.3 配置与版本管理

Scenario、路网、车流、算法、模型和事件配置应具有独立版本。实验启动后，其输入配置应冻结或生成不可变快照，避免配置被修改后无法复现实验结果。

### 4.4 并发事件和冲突处理

明确：

- 多个事件作用于同一路段时容量如何计算；
- 道路封闭与应急保障冲突时谁优先；
- 活动流量倍率和交通负荷倍率是否相乘；
- 事件撤销后恢复原值还是重新计算当前有效事件；
- 已结束事件能否重新启用；
- 同一事件重复注入是否幂等。

### 4.5 信号控制安全约束

除最小绿和最大绿外，还应明确：

- 黄灯时长；
- 全红清空时间；
- 冲突相位矩阵；
- 相位最短保持时间；
- 行人或非机动车相位是否建模；
- 控制命令过期、重复或乱序时的处理；
- 恢复到 Fixed-Time 时的安全过渡方式。

### 4.6 实验任务状态

建议为 `ExperimentRun` 明确状态机，例如：

```text
queued → preparing → running → aggregating → completed
                    ↘ failed / cancelled / degraded
```

每个终态应规定结果是否有效、是否进入统计、是否允许重跑以及原始文件保留规则。

### 4.7 WebSocket 可靠性

增加消息版本、序号、会话 ID、仿真时间和幂等键；说明断线重连、消息丢失、重复消息、乱序消息和全量状态补偿机制。

### 4.8 权限和审计

明确赛事单机演示和后续多用户部署是否采用不同安全级别。至少定义：

- 查看、控制、事件注入、算法切换和报告下载权限；
- Agent 工具调用的操作者身份；
- API 密钥和模型密钥管理；
- 审计日志保存期限及敏感参数脱敏；
- 高风险操作的确认或撤销机制。

### 4.9 数据来源与适用性声明

说明路网、OD、信号配时和交通流数据的来源、时间范围、授权方式、脱敏情况以及真实性级别。对于校准数据和合成数据应明确区分，避免将模拟数据描述为实时真实交通数据。

## 5. 建议建立需求追踪表

每项正式需求应具有唯一编号，并能够追踪到实现模块、测试用例和交付证据。

| 需求编号 | 需求摘要 | 优先级 | 实现模块 | 测试用例 | 交付证据 | 状态 |
|---|---|---:|---|---|---|---|
| SCN-001 | 加载 20+ 可控路口的目标路网 | P0 | 场景服务 | TC-SCN-001 | 路网摘要、运行日志、截图 | 待确认 |
| EVT-001 | 注入并撤销施工占道事件 | P0 | 事件中心 | TC-EVT-001 | API 结果、事件日志、仿真录像 | 待实现 |
| ALG-001 | Fixed-Time 统一基线 | P0 | 算法管理 | TC-ALG-001 | 配置快照、原始结果 | 待实现 |
| BEN-001 | 运行标准实验矩阵 | P0 | Benchmark | TC-BEN-001 | 任务清单、CSV、统计摘要 | 待实现 |
| SAF-001 | 模型异常时安全降级 | P0 | 控制与降级模块 | TC-SAF-001 | 故障注入记录、降级日志 | 待实现 |

完整追踪表应覆盖全部 P0 和 P1 需求。没有测试用例和交付证据的条目，不应标记为“已完成”。

## 6. v0.2 推荐修订清单

### 第一优先级：形成可执行基线

1. 定义 Proposed 协同方案的组成、权限和接口；
2. 将全部 P0 验收条件改为可测量指标；
3. 统一随机种子、重复实验和统计计算口径；
4. 增加本期范围、非目标和适用性声明；
5. 为所有核心需求分配唯一编号；
6. 建立需求—实现—测试—证据追踪表。

### 第二优先级：补齐工程契约

1. 明确时间、标识、坐标和单位；
2. 定义核心数据对象字段和版本策略；
3. 明确并发事件和控制冲突规则；
4. 完善信号安全约束和降级状态机；
5. 完善 Benchmark 任务与 WebSocket 消息状态；
6. 明确权限、审计和数据来源要求。

### 第三优先级：优化文档结构

1. 区分需求、设计建议、技术约束和验收规则；
2. 将项目现状评价与正式需求分离；
3. 将详细 API schema 和算法接口移入设计文档；
4. 将实验公式、测试步骤和判定阈值移入测试规程；
5. 为赛事答辩单独形成 5–8 分钟演示脚本。

## 8. 结论

当前 v0.1 已具备较好的项目全景描述能力，核心方向和优先级基本合理。下一阶段不宜继续扩充算法或功能清单，而应优先消除方案边界、验收阈值、统计口径和范围定义上的歧义。

完成本评审提出的五项第一优先级修订后，文档即可作为 v0.2 需求基线，用于开发排期、接口设计、测试用例编写和比赛验收准备。后续开发中，应坚持以可运行闭环和可复现实验为主线，确保每一项核心能力都有代码实现、测试记录和可展示证据。
