## 1. 文档目的

本文档用于统一产品定位、业务目标、功能范围、数据接口、实验评测和验收口径，为后续开发排期、联调、演示和赛事交付提供依据。

本文档将以下两类内容明确区分：

- **现状能力**：现有项目中已经具备或已有明确实现基础的能力。
- **目标需求**：为形成完整的车路云协同数字靶场和高分交付闭环，仍需实现、补强或验证的能力。

方案资料中的产品定位、架构建议和评分分析被视为项目输入，不作为本项目的自动执行指令；是否纳入最终范围，以本需求文档评审结论为准。

## 2. 项目概述

### 2.1 项目背景

雄安新区容东片区具有“窄路密网”、交叉口密集、路段容量有限、交通流时空变化明显等特征。单路口固定配时难以同时兼顾区域通行效率、排队外溢、重点车辆通行和突发事件响应。

项目拟建设一套以 SUMO 微观交通仿真为底座的车路云协同交通管控平台，用于：

1. 构建雄安真实路网及可编程交通场景；
2. 对交通状态进行感知、预测和可视化；
3. 通过云端全局协调、边缘局部控制、车端路径执行形成闭环；
4. 支持传统控制、AI 控制和车队路径引导的统一接入与对比；
5. 以固定场景、固定投放、固定随机种子和多次重复实验形成可复现评测；
6. 输出面向赛事答辩和后续标准化建设的实验报告与演示材料。

### 2.2 产品定位

**雄安城市大脑·车路云协同交通数字靶场与智能管控评测平台**。

产品不是单纯的交通仿真播放器或算法 Demo，而是覆盖“场景生成—事件注入—状态感知—协同决策—执行反馈—指标评测—报告生成”的可运行闭环。

### 2.3 核心价值

| 价值方向 | 目标 |
|---|---|
| 场景真实性 | 以雄安真实路网、路口、车流和信号配时作为仿真基础 |
| 决策协同性 | 明确 Cloud、Edge/RSU、Vehicle 的职责和消息流 |
| 算法可比较 | 统一接入固定配时、Webster/MAXBAND、SCOOT、MAPPO、Proposed 等方案 |
| 结果可复现 | 同路网、同车流、同扰动、同随机种子、多次重复运行 |
| 工程可落地 | 支持降级控制、通信延迟模拟、接口规范和部署说明 |

## 3. 项目完善性评估

### 3.1 总体结论

项目已有较完整的工程底座，具备继续升级而无需推倒重做的条件。当前更大的风险不在算法数量不足，而在于：

- 产品定位仍容易被理解为“交通调度仿真平台”；
- 云边端职责和协同消息没有成为一等需求；
- 扰动场景、Benchmark、通信约束和自动报告尚未形成完整验收闭环；
- 已有指标和实验结果较多，但实验矩阵、基线、统计显著性和报告口径需要统一；
- 赛事演示模式与开发调试界面尚需分离。

### 3.2 已具备能力

| 领域 | 已有基础 | 评估 |
|---|---|---|
| 仿真底座 | SUMO、雄安 20 路口网络、车流与信号文件 | 基础完整 |
| 后端服务 | FastAPI、REST、WebSocket、仿真会话和指标采集 | 基础完整 |
| 前端展示 | Vue 3、Canvas 路网、车辆/信号灯、指标面板、方案面板 | 基础完整 |
| 算法 | Webster、MAXBAND、SCOOT、MAPPO、STGCN、动态 Dijkstra、K 短路/车队引导 | 算法覆盖较全 |
| 智能体 | LLM Agent、工具调用、安全参数校验、报告生成 | 有特色，需纳入主流程 |
| 工程化 | Docker、启动脚本、模型权重、ONNX 转换和部署验证 | 基础较好 |
| 实验 | 固定配时、SCOOT、MAPPO 对比，热点场景和负荷校准 | 有数据，但需标准化 |
| 文档 | 需求、系统设计、接口、实验评估、典型路口文档 | 材料齐全，需建立统一需求基线 |

### 3.3 主要缺口与优先级

| 缺口 | 影响 | 优先级 | 完成判定 |
|---|---|---:|---|
| Fixed-Time 统一基线 | 无法完整证明算法增益 | P0 | 可在同一实验配置下运行并记录结果 |
| 扰动事件中心 | 无法体现“数字靶场”和突发响应 | P0 | 施工、封闭、大型活动、事故至少可配置注入 |
| Cloud-Edge-Vehicle 协同模型 | 产品叙事与赛题目标不够清晰 | P0 | 角色、消息、控制边界、降级策略可展示 |
| Benchmark 执行器 | 实验依赖人工，结果不可批量复现 | P0 | 支持算法×场景×负荷×种子×重复次数矩阵 |
| ≥20 路口稳定验收 | 不能证明城市级场景能力 | P0 | 启动、运行、控制、停止连续通过 |
| 多维指标 | 只有效率指标，评估不完整 | P1 | 增加 P95 等待、油耗/CO₂、安全或工程指标 |
| V2X 延迟/丢包 | 难以证明通信约束下的鲁棒性 | P1 | 可配置并进入实验报告 |
| 自动化报告 | 难以形成标准化成果 | P1 | 生成 CSV/JSON/HTML，PDF/Word 可选 |
| AB 同屏演示 | 评委难以直观看到效果 | P1 | 同场景同步展示基线和 Proposed |
| 标准测试规程 | 项目价值难从“平台”升维 | P1 | 输出测试流程、输入输出、指标与判定规则 |

### 3.4 完善性结论

项目可以判定为：**工程底座基本完善，产品闭环和交付验收体系尚未完全完善**。建议以 P0 项为下一阶段验收门槛；在 P0 完成前，不建议继续扩展更多算法种类。

## 5. 典型业务场景

### 5.1 正常早高峰

用于验证固定配时、Webster/MAXBAND、SCOOT、MAPPO 和 Proposed 的基础差异。

### 5.2 临界负荷与区域热点

中心区域交通需求升高、外围相对畅通，验证自适应信号能否将绿时和通行能力导向高需求区域。

### 5.3 大型活动散场 + 施工占道（主演示场景）

大型活动导致局部流量突增，同时施工造成道路容量下降。系统应完成：

```text
事件注入 → 状态感知 → STGCN 预测 → Cloud 区域协调
→ Edge 路口控制 → Vehicle 动态重路由 → 指标恢复
```

### 5.4 应急车辆保障

对救护车、消防车或其他优先车辆提供路线引导、信号优先或区域协调，并展示普通交通影响。

### 5.5 通信受限运行

模拟延迟、抖动、丢包和云端不可用，验证边缘控制和安全降级能否维持基本交通服务。

## 6. 总体架构需求

### 6.1 分层架构

```text
前端数字驾驶舱
        ↓
Benchmark 评测中心 / 报告中心
        ↓
Cloud：全局感知、预测、区域协调、全局路由
        ↓
Edge/RSU：单路口与局部路网实时控制、降级运行
        ↓
Vehicle：状态上报、路线执行、动态重规划、优先车辆任务
        ↓
SUMO：路网、车辆、信号、扰动、V2X 仿真
```

### 6.2 现有算法的归属建议

| 层级 | 主要职责 | 可复用能力 |
|---|---|---|
| Cloud | 全局状态、短时预测、区域拥堵识别、走廊协调 | STGCN、MAXBAND、全局指标、动态路由 |
| Edge/RSU | 路口和局部路网信号控制 | MAPPO、SCOOT、Webster、TOD |
| Vehicle | 路径执行、重路由、车队约束和优先任务 | Dijkstra、K 短路、负载均衡 |
| Safety fallback | AI/通信异常时维持可控运行 | SCOOT、固定配时、最小/最大绿约束 |

### 6.3 协同闭环要求

系统应能够展示并记录：

1. Cloud 获取全局交通状态并生成预测；
2. Cloud 生成区域级控制建议或策略；
3. Edge 根据本地队列和信号状态执行控制；
4. Vehicle 接收路径建议并反馈执行状态；
5. 仿真状态变化回传至 Cloud/Edge；
6. 任意控制动作具备来源、时间、目标对象和结果记录。

## 7. 功能需求

### 7.1 场景工厂

**目标**：提供可复现、可参数化的雄安交通数字场景。

| 编号 | 需求 | 优先级 | 验收要点 |
|---|---|---:|---|
| SCN-001 | 加载雄安目标路网并提供摘要 | P0 | 至少包含 20 个可控交叉口；返回 edge、lane、TLS 数量 |
| SCN-002 | 支持 OSM/SUMO 路网接入和 GeoJSON 导出 | P1 | 前端可渲染，属性包含道路、节点、车道和限速信息 |
| SCN-003 | 配置 OD、车辆数、投放时间和交通负荷 | P0 | 支持 80%/100%/120%/150% 或等价负荷档位 |
| SCN-004 | 支持小客车、公交、货车、应急车辆等类型 | P1 | 车辆类型进入仿真并在指标中可区分 |
| SCN-005 | 固定随机种子生成可复现实验车流 | P0 | 相同配置生成同一车流文件或等价状态 |
| SCN-006 | 配置早高峰、平峰、晚高峰、夜间时段配时 | P0 | 时段切换和手动覆盖可验证 |

### 7.2 扰动事件中心

事件对象至少包含 `event_id`、`event_type`、作用对象、开始时间、结束时间、影响参数、注入者和状态。

| 事件 | 最低配置要求 |
|---|---|
| 施工占道 | edge/lane、容量下降或封闭比例、持续时间 |
| 道路封闭 | edge、方向、开始/结束时间 |
| 交通事故 | edge、容量下降比例、清障时间 |
| 大型活动 | 区域、OD/流量倍率、持续时间 |
| 学校/园区潮汐 | 区域、时段、流量倍率 |
| 信号异常 | 路口、异常类型、恢复时间 |
| 通信异常 | 延迟、抖动、丢包率、作用层级 |
| 应急保障 | 车辆、起终点、优先级、保障时间窗 |

功能要求：

- 支持前端、REST API 和 Agent 三种注入方式；
- 注入前校验目标对象和参数范围；
- 支持事件列表、详情、启停、撤销和历史查询；
- 事件触发后通过 WebSocket 推送，并进入实验结果元数据；
- 同一实验中事件顺序和时间必须可复现。

### 7.3 仿真会话与控制

沿用现有 `idle/running/paused/stopped/error` 生命周期，并补充：

- 每个会话关联 `scenario_id`、`algorithm_id`、`seed`、`experiment_id`；
- 启动前完成路网、车流、模型和依赖自检；
- 支持启动、暂停、恢复、停止、单步、调速和安全退出；
- 发生 SUMO、模型或接口异常时记录错误并按配置降级；
- 会话停止后保留可查询的摘要结果。

### 7.4 算法管理与控制

#### 7.4.1 统一算法接口

所有算法应支持：`init`、`on_step`、`on_metrics`、`handle_action`、`cleanup`，并声明：

- 算法 ID、名称、版本和适用场景；
- 输入观测契约、控制动作契约；
- 决策周期和最大耗时；
- 所需模型文件及模型版本；
- 失败时的 fallback 策略。

#### 7.4.2 基线与方案

最低支持以下可比较方案：

1. Fixed-Time 固定配时；
2. Webster + MAXBAND；
3. SCOOT-like 自适应控制；
4. MAPPO + STGCN；
5. Proposed Cloud-Edge-Vehicle 协同方案；
6. 受限车队动态路径引导方案。

#### 7.4.3 安全降级

- MAPPO 模型缺失、维度不匹配、推理超时或输出非法时自动转入 SCOOT 或固定配时；
- Cloud 不可用时 Edge 继续执行本地控制；
- Edge 失联时保持最近有效配时并遵守最大绿、最小绿和防饥饿约束；
- 所有降级动作必须进入事件日志和实验报告。

### 7.5 云边端协同

系统需提供逻辑上的三类节点，即使初期部署在同一进程或容器中，也必须在数据模型和日志中区分来源。

| 节点 | 输入 | 输出 |
|---|---|---|
| Cloud | 全局路况、历史序列、事件、实验配置 | 预测、区域策略、走廊方案、路由建议 |
| Edge/RSU | 路口本地车辆、队列、信号相位、Cloud 策略 | 相位/绿灯动作、本地状态 |
| Vehicle | 车辆状态、道路状态、路由建议 | 轨迹执行、重规划、优先任务状态 |

### 7.6 V2X 通信仿真

至少支持配置：`latency`、`jitter`、`packet_loss`、`bandwidth`（带宽可作为增强项）。通信消息应包含消息 ID、发送方、接收方、仿真时间、生成时间、到达时间、过期时间和载荷类型。

首期验证档位建议为：0ms、50ms、100ms、200ms；丢包率 0%、1%、5%、10%。

### 7.7 可视化驾驶舱

- 路网、车辆、信号灯和事件在同一地图上展示；
- 展示 Cloud、Edge、Vehicle 当前状态和最近动作；
- 展示平均延误、排队、速度、吞吐、完成率等 KPI；
- 支持最堵道路/路口定位和车辆详情；
- 提供开发模式和比赛演示模式；
- 比赛演示模式支持 Baseline vs Proposed AB 同屏，确保同路网、同车流、同事件和同随机种子；
- 对关键动作显示“感知→决策→执行→反馈”链路。

### 7.8 LLM Agent

LLM Agent 作为交互入口，不直接绕过安全校验修改仿真状态。最低支持：

- 查询全局、路口、道路和事件状态；
- 注入事件；
- 规划路径；
- 切换或配置算法；
- 读取前后对比；
- 生成实验报告；
- 工具白名单、参数范围校验、调用上限和失败回填。

Agent 的每次工具调用应记录用户指令、工具、参数、结果、仿真时间和执行耗时。

### 7.9 Benchmark 评测中心

支持创建实验配置：

```json
{
  "scenario_id": "rongdong_event_construction_001",
  "traffic_demand": 1.2,
  "events": ["construction", "large_event"],
  "algorithms": ["fixed_time", "scoot", "mappo", "proposed"],
  "seeds": [42, 43, 44, 45, 46],
  "repetitions": 5,
  "warmup_seconds": 90,
  "duration_seconds": 480
}
```

评测中心应支持：

- 场景、负荷、扰动、算法、通信条件、随机种子和重复次数的组合配置；
- 批量排队、暂停、继续、取消和失败重跑；
- 统一 warmup、采样和有效窗口；
- 输出均值、标准差、P50/P95、提升比例和一票否决项；
- 结果与代码版本、模型版本、路网版本、配置文件和运行环境绑定；
- 生成 CSV、JSON、HTML，PDF/Word 作为交付增强项。

## 8. 指标与评估要求

### 8.1 效率指标

- 平均旅行时间；
- 平均延误；
- 平均速度；
- 吞吐量/到达量；
- 平均排队长度、最大排队长度；
- 平均等待时间、P95 等待时间；
- 完成率。

### 8.2 环境与安全指标

优先接入 SUMO 可获得的油耗和 CO₂ 排放；安全指标至少选择一项：TTC、冲突次数、急刹车次数或最小车头时距。

### 8.3 工程指标

- Cloud/Edge/Vehicle 决策耗时；
- API 响应延迟；
- V2X 端到端延迟和丢包率；
- 模型推理耗时；
- 仿真实时倍率/FPS；
- CPU、内存和显存占用；
- 异常恢复和降级耗时。

### 8.4 评价原则

1. 同场景、同路网、同车流、同事件和同随机种子进行对比；
2. 结果至少报告均值与标准差，关键指标报告 P95；
3. 低负荷“都不堵”和超饱和“都堵死”不作为唯一主实验，应优先选择临界负荷和空间不均场景；
4. 综合评分可沿用效率、稳定、公平的加权方式，但不得替代原始指标；
5. 结果必须保留原始数据、配置和复现实验命令。

| `/experiments` | Benchmark 创建、启动、状态和取消 |
| `/experiments/{id}/results` | 实验结果和统计摘要 |
| `/reports` | 报告生成、下载和元数据 |
| `/health` | 服务、SUMO、模型、消息链路健康状态 |

WebSocket 应增加或规范以下消息类型：`event_injected`、`cloud_decision`、`edge_action`、`vehicle_route_update`、`communication_degraded`、`fallback_activated`、`benchmark_progress`。

### 9.3 错误与审计

所有控制类接口必须返回结构化错误码；控制动作、事件、降级、模型加载和实验运行均应产生审计日志。日志至少包含时间、会话、用户/Agent、动作、目标、参数摘要、结果和耗时。

## 10. 非功能需求

### 10.1 性能

- 20+ 路口场景能够稳定运行；
- 实时展示不因单个客户端视域外车辆数量线性失控；
- 支持车辆、信号灯和指标推送频率分别配置；
- 算法决策不得阻塞 API 和 WebSocket 服务；
- Benchmark 任务支持后台执行并报告进度。

### 10.2 可靠性

- 仿真异常、模型异常和通信异常必须可检测；
- 有明确的 fallback，不能因 AI 或 LLM 失败导致仿真失控；
- 停止仿真后释放 TraCI、线程、文件和容器资源；
- 关键结果落盘，服务重启后不影响已完成实验结果。

### 10.3 可复现性

实验必须记录路网、车流、事件、算法、模型、代码提交、配置、随机种子、依赖版本和运行平台。

### 10.4 可维护性与扩展性

- 新算法通过统一接口接入，不修改核心仿真生命周期；
- 新事件通过事件类型和参数校验扩展；
- 前端指标、消息类型和算法状态采用可配置 schema；
- Docker 和 Windows 一键启动继续保留。

### 10.5 安全性

- Agent 工具使用白名单；
- 外部参数进行类型、范围和目标对象校验；
- API 密钥、模型密钥和 `.env` 不进入版本库；
- 报告下载和实验控制接口具备基本权限隔离预留。

## 11. 验收方案

### 11.1 P0 验收门槛

1. 20+ 路口雄安路网可一键启动并运行 10 分钟以上；
2. Fixed-Time、SCOOT、MAPPO/降级方案均可在同一车流下运行；
3. 施工占道、大型活动、道路封闭至少三类事件可注入、撤销和记录；
4. Cloud、Edge、Vehicle 的状态、动作和反馈可在日志或界面中追踪；
5. Benchmark 可运行至少 4 类场景 × 3 档负荷 × 4 种算法 × 5 个种子；
6. 输出平均值、标准差、P95 和原始结果；
7. 任一模型缺失或推理异常时可安全降级；
8. 同配置重复运行结果在允许误差范围内一致。

### 11.2 P1 验收门槛

1. 支持 V2X 延迟/丢包配置并进入实验报告；
2. 支持油耗、CO₂ 和至少一项安全指标；
3. 支持 AB 同屏演示；
4. 自动生成 HTML/CSV/JSON 报告，具备 PDF/Word 导出能力；
5. 形成《车路云协同交通管控系统仿真测试规程建议稿》；
6. 完成 5–8 分钟稳定演示流程。

## 13. 开发优先级与后续决策

### P0

Fixed-Time 基线、20+ 路口稳定运行、事件中心、云边端数据模型、Benchmark、可复现实验和安全降级。

### P1

V2X 通信仿真、油耗/CO₂、安全指标、AB 同屏、自动报告和测试规程。

### P2

进一步模型调参、更多路网域随机化、UI 动画和视觉优化。

在 P0 验收完成前，不建议优先增加第四、第五套算法；应优先把现有 MAPPO、STGCN、SCOOT、Webster、MAXBAND 和路径引导组织成可运行、可比较、可量化的完整产品。

## 14. 待评审问题

以下问题需要项目负责人或赛事要求最终确认：

1. “20+ 路口”是否为赛事硬性要求，还是当前方案建议目标；
2. Proposed 方案的具体控制动作边界由 Cloud、Edge 还是统一后端负责；
3. 安全指标采用 TTC、急刹车还是冲突次数；
4. Benchmark 的标准仿真时长、warmup 和重复次数；
5. 是否需要真实 RSU/车端硬件，或软件逻辑仿真即可；
6. PDF/Word 报告是否为最终提交硬要求；
7. 评测综合评分公式和一票否决阈值是否需要由赛事官方口径覆盖。
