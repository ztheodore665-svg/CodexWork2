# 多 Agent 最小演示（能跑，不需要 API Key）

> 一句话：**前台接活 → 叫对口的专员 → 专员干完 → 校对员检查 → 不合格打回重做。**
> 这就是多 Agent 的全部骨架。剩下的都是在这五个动作上加东西。

## 跑起来

```bash
python research/experiments/multi_agent_demo/orchestrator.py
```

无依赖、无网络、无数据库。五个场景会逐个打印"谁在什么时候做了什么"。

## 五个场景分别在演示什么

| 场景 | 谁接的 | 演示的概念 |
| --- | --- | --- |
| "去年秋天去了哪些古镇？" | 时间线管家 | **路由**：这类问题本机就能答，不该调模型 |
| "总结一下这趟的风格" | 总结员 | **质检打回**：有一句没引用，校对员抓出来，删掉那句再交 |
| "照着上次规划一个周末" | 规划师 | **不同角色不同标准**：规划是建议，不要求逐句引用 |
| "我在南极看过企鹅吗？" | 求证员 | **主动拒答**：找不到证据就说找不到，不编 |
| "帮我订去巴黎的机票" | 没人接 | **能力边界**：不归它管的事，明确说不做 |

## 五个必须有的零件

1. **前台（Orchestrator）**：只做三件事——听需求、选人、决定什么时候停。
2. **专员（Specialist）**：每人只管一类问题，有自己的工具和数据权限。
3. **共享黑板（Board）**：所有人读写同一份状态，谁改了什么都能打印出来。
4. **校对员（Auditor）**：不生成，只检查；它有权把结果打回或拦下。
5. **停止条件**：最多重做 1 次（`max_rounds=2`），还不过就拒答。没有这条，就是无限循环。

## 它不是什么

- **不是 LLM**：专员目前用规则实现，目的是让你先看清"协作结构"。把 `handle()` 里换成一次 LLM 调用，结构一点不用改。
- **不是生产代码**：没有并发、没有超时、没有重试、没有 trace。这些在真实系统里由 `agent/pipeline.py` 和 `observability.py` 负责。
- **不是"Agent 越多越好"**：三个 Agent 问同一件事，只是把一次调用变成三次，判断并不会更准。**分工必须带来不同的信息或不同的权限**，否则就是烧钱。

## 对应到你的真实系统

| 演示里的角色 | 真实系统里的谁 | 现状 |
| --- | --- | --- |
| 前台 | `QueryParseNode` 的意图分类 + 路由 | 已有意图分类，缺"显式路由" |
| 时间线管家 | L0 本机结构化查询 | 待做（D5） |
| 总结员 | L1 薄引擎 `ThinAnswerService` | 已写好（8 条测试） |
| 规划师 | L2 规划类生成 | 已有 RAG 可复用 |
| 求证员 | `self_check` + 拒答 | 已有，但只在生成后校验 |
| 校对员 | `SelfCheckNode` + 审计 | 已有结构校验，语义审计待做 |
| 黑板 | `PipelineState` | 已有 |

**所以"能不能实现多 Agent"的答案是：你的系统已经有 70%，缺的是把它显式化、把路由和交接打印出来、让每个专员有独立的工具权限。**

## 三个档次的实现野心

| 档次 | 工作量 | 做什么 | 答辩时怎么说 |
| --- | --- | --- | --- |
| 最小 | 1 天 | 把现有节点改名成 Agent，路由日志打出来 | "我们有四个角色"（偏弱，容易被认为是包装） |
| **推荐** | 3 天 | 前台 + 4 专员 + 校对员；升级要用户同意；每个专员独立 prompt | "多 Agent 的收益是权限隔离与可质检，不是更聪明" |
| 亮点 | 1 周 | 加"反驳员"：专门找反证，与总结员形成对抗，再由校对员裁决 | "我们用消融证明：异质信息集比同角色多票更有效" |

## 三句常见误解

1. **"多 Agent 就是多叫几个模型聊天"** —— 不是。没有分工、没有权限差异、没有质检，就只是重复调用。
2. **"Agent 越多越智能"** —— 不是。多一个 Agent 就多一次失败点、多一份延迟、多一份成本。
3. **"多 Agent 一定要用框架"** —— 不是。这个演示 200 行纯 Python，没有任何框架；框架解决的是持久化与可视化，不是协作本身。
