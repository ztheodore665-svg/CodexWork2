# 阶段 7：语义抽象、群体推荐与可验证断言

> 科研轨（设计文档 §9）。**本阶段不宣称联邦学习** —— 隐私收益来自
> "语义抽象 + 序列截断 + k-匿名门禁"三重机制的叠加，而不是参与方数量。
> 参与者规模是数十人量级，把聚合器叫成"联邦学习"会误导读者高估其隐私保障。

## 1. 为什么必须先做语义抽象（W7-1）

群体推荐最直觉的写法是"基于具体地点"：

```
去过龙门石窟的人，接着去了老君山  →  推荐老君山
```

这条记录本身就是**重识别攻击的入口**。龙门石窟的游客本就有限，
一条 `龙门石窟 → 老君山` 的记录几乎能把一个自然人从人群里挑出来；
再叠加日期（"五一前后"）和一个大概的城市，重识别是必然而不是风险。

抽象成 `heritage → nature` 之后，同一条模式会被**大量**行程命中：
任何"看了人文景点之后去爬山"的行程都会贡献同一个 `heritage → nature`。
这时一条模式记录对应的人群是"所有这么玩过的人"，单条记录不再指向个体。

**隐私收益来自泛化，而不是来自加密**：加密只改变数据的存在形式，
泛化改变的是数据里"有多少可区分信息"。坐标模糊到城市也救不了基于地点的
协同过滤 —— 因为唯一性来自**组合的基数**，不是单点的精度。

设计文档 §9.1 的两条示例行程：

```
洛阳：      heritage → heritage → nature → heritage
苏州—上海：  watertown → watertown → metropolis → metropolis
```

抽象掉地点名之后，"人文之后去看自然"是一条可以在成千上万条行程上统计的规律，
而"龙门石窟之后去老君山"永远只属于少数人。

### 1.1 词表的两类词：泛化 vs 纠偏

`app/utils/semantic_tags.py::TAG_KEYWORDS` 里刻意混着两种词：

| 类型 | 例子 | 作用 |
| --- | --- | --- |
| 单字 / 后缀词 | `寺` `山` `江` `湖` | **泛化**：长尾地名不可能逐个收录，靠后缀兜住 |
| 整名 | `清明上河园` `王府井` `丽江古城` | **纠偏**：单字泛化必然误伤 |

纠偏之所以生效，靠的是 `semantic_service._break_tie()` 的**平票修正**：
整名与单字各得 1 票形成平票，命中词更长的那一类胜出。
所以**整名必须比它可能误伤的那个单字更长** —— 这是本词表的维护纪律。

本轮实测出的四类误伤与修正：

| 地点 | 只靠单字 | 修正后 | 原因 |
| --- | --- | --- | --- |
| 清明上河园 | `nature`（命中"河"） | `heritage` | 它是人文景区 |
| 王府井 | `heritage`（命中"王府"） | `metropolis` | 它是商圈 |
| 丽江古城 | `heritage`（命中"古城"）+ `nature`（"江"）三义 | `watertown` | 它是水乡 |
| 欢乐谷 | `nature`（命中"公园"） | `leisure` | 它是游乐场 |

同时补齐了一批不含通名、完全漏判的知名地点：`故宫`、`东方明珠`、
`回民街`、`兵马俑`、`颐和园`、`九寨沟`。

词表是有限的。**收录不到的地名诚实返回 `None`，绝不猜**：
猜错的语义会顺着模式库污染群体推荐，而"没有语义"只是少一条数据。

> ⚠️ 词表变更必须同步升 `SEMANTIC_TAG_VERSION`（本轮 `sem-2026.1` → `sem-2026.2`），
> 并同步 `core/config.py::semantic_tag_version` 与 `app/data/semantic_tags.yaml`。
> 已落库的语义序列是按旧版抽的，拿新版规则去解释旧序列会得到错误的模式。

### 1.2 两个"序列"不是一回事

| | `semantic_sequence_for_trip()` | `extract_sequences()` |
| --- | --- | --- |
| 每个地点 | **一个标签**，不合并 | 合并相邻的相同标签 |
| 输出 | `["heritage", "heritage", "nature"]` | `[("heritage", "nature")]` |
| 用途 | **展示**：这就是这趟行程的语义轨迹 | **挖掘**：喂给模式库统计 `support` |

为什么两个都要：展示时"连着逛了两个石窟"占了两站，是有信息量的；
而挖掘时必须合并 —— 否则 `heritage→heritage→nature` 会多出一条
几乎无人命中的 `(("heritage","heritage"), "nature")` 模式，白白稀释支持度。

**用错方向的代价真实可见**：拿展示序列去 `submit()` 模式库会碎成一片；
拿合并后的序列去展示，用户会以为自己少去了几站。
`test_sequence_differs_from_pattern_mining_sequence` 专门钉住这个区别。

## 2. k-匿名门禁（W7-2）

### 2.1 三道防线

| 环节 | 拦什么 |
| --- | --- |
| 泛化 | 抹掉地点名，只留语义 |
| 截断（最后 6 步） | 长历史本身就是指纹（6^20 组合 practically 全球唯一） |
| 门禁（`support >= 5`） | 样本量不足的模式不可见 |
| 防刷（`user_key` unique） | 同一人对同一模式只贡献一次 |

**为什么是 5**：k-匿名里 k 的取值。取小了匿名集不够，取大了在"单用户起步"的
产品早期永远出不了第一条推荐。5 是隐私效用与可用性折中的常用量级。

**门禁必须逐模式判定**：一条模式达标不会顺带把别的模式放出来。
把门禁实现成"全局样本量 >= k 就放行"是最容易犯的错 ——
那样只要全站累计到 5 条上报，任何 `support=1` 的模式都会被当共识发出去，
而 `support=1` 意味着"有一个人这么走过"，把它公开正是 §9 要防的。

### 2.2 实测：门禁恰好卡在第 5 条

```
查询序列 [heritage]，逐条注入匿名观测：
  注入第 1 条 | tag=None     | 暂无足够匿名模式支撑（需要至少 5 次匿名观测）
  注入第 2 条 | tag=None     | 暂无足够匿名模式支撑
  注入第 3 条 | tag=None     | 暂无足够匿名模式支撑
  注入第 4 条 | tag=None     | 暂无足够匿名模式支撑
  注入第 5 条 | tag=nature   | 已匹配到满足 k-匿名门禁的群体模式
  注入第 6 条 | tag=nature   | 已匹配到满足 k-匿名门禁的群体模式
响应字段 = ['avg_score', 'confidence', 'k', 'message', 'tag', 'version']
响应里有没有 support 字段: False
```

### 2.3 三条接口语义（容易写错，逐条说明）

- **未达标 → `200 + tag=None`**，不是 404 / 422。
  k-匿名门禁的结论是"**没有结论**"，不是"请求非法"。
  用 404 还会和"开关关闭"撞码，前端无法区分"功能没开"和"数据不足"。
- **开关关闭 → 404**，不是 403。未启用的能力对外应当表现为**不存在**；
  403 等于把未来的攻击面先画在地图上。
- **序列里的非法标签静默丢弃**，但**过滤完什么都不剩 → 422**。
  匿名上报里混进未知标签是常态，为一个脏标签拒绝整条上报，
  丢掉的是一条本可以贡献给匿名集的数据。

### 2.4 `support` 绝不出网

`SemanticRecommendation` 从**数据结构上**就不带 `support`，杜绝上游手滑把它
塞进响应。`confidence` 是相对占比（该模式 support / 该前缀下全部候选 support
之和），外部拿到 `0.6` 无法反推背后是 3 人还是 3000 人。

`test_response_never_leaks_exact_support` 用"响应字段集合精确相等"来断言 ——
将来有人往 schema 里加一个 `support` 字段，这里会立刻红。

## 3. 可验证断言面板（W7-3）

### 3.1 颜色只表达"证据强度"

| 颜色 | 语义 | 触发条件 |
| --- | --- | --- |
| 🟢 绿（pass） | 本机找到了**证实**证据 | Ed25519 验签通过 / SHA256 承诺一致 / 链连续 |
| 🔴 红（fail） | 本机找到了**证伪**证据 | 验签不通过 / 承诺不一致 / 链断裂 |
| ⚪ 灰（unknown） | 本机**没有**证据 | 缺承诺字段 / 跨设备链未锚定 |

三种颜色的区别是**密码学语义，不是装饰**。密码学 UI 的红线是
"不能把'没验证'说成'验证失败'"：跨设备收到的信物（prevHash 指向对方机器上的
链头）在收件人这边必然判不出来，这是协议的预期行为，不是文件被动过手脚。
把它涂红会让用户以为信物不可信，进而怀疑整套端到端加密。

**一句话：红 = 证伪，灰 = 未证实，绿 = 证实。三者互不替代。**

### 3.2 测试环境的两个坑（值得记下来）

1. **`fireEvent.change(input, { target: { files } })` 静默失效**。
   `input.files` 是只读的 FileList，没有 setter，赋值不报错也不生效，
   组件读到 `files[0] === undefined`，什么事都不发生。
   必须用 `Object.defineProperty(input, 'files', { value: [file] })`。
2. **jsdom 的 `File` 没有 `.text()`**（标准是有的，Chrome 76+ / Safari 14+ 都支持）。
   不补这个洞，`await file.text()` 抛 TypeError 被 catch 兜成"读不出这个信物"，
   于是每条用例都只能测到"打不开"这一条路径。
   测试里用 `FileReader` 补上（这是测试环境缺口，不是产品缺陷）。

另外：**`waitFor` 要等"结果出现"，不要等"loading 消失"**。
`verifying` 在第一轮 render 之后才翻 true，"找不到『正在验证』"在异步开始之前
就已经成立，waitFor 会立刻通过，断言随即跑在状态更新之前。

## 4. 阶段 6 的两条尾巴

### 4.1 `POST /api/v1/trips`（新建空旅程）

此前 `GET /trips` 是唯一的行程接口，"新建旅程"按钮只能**禁用**并写明原因。
禁用不是设计风格，它只是"还做不到"的临时标记 —— 接口一到位就该撤掉。

**关键约束：手工行程不能被后续导入冲掉。**
`rebuild_user_trips()` 重建行程时**只删 `source == cluster` 的行**。
用户敲下的标题是库里唯一的副本，删了找不回来：
**派生数据可以让位，用户输入不行**。
`test_manual_trip_survives_a_rebuild` 用一条真的连库的用例钉死它
（这个 bug 不报错，只在"我建的旅程不见了"时被发现）。

配套改动：`rebuild_user_trips()` 现在返回**全部**行程（手工 + 新建），
顺序与 `list_user_trips` 一致 —— 否则导入回执的 `trip_ids` 与 `GET /trips`
会给出不同答案，而这种不一致只在"导入后列表看起来少了一趟"时被人发现。

### 4.2 语义标签缺失的兜底提示

导入那一刻照片还没有描述文本，后端诚实返回 `semanticTag = null`，
前端 `itemToPlace()` 把它**静默**退回 `leisure`。打包照样成功、收件人照样能解开 ——
于是"这个地点其实没被分类过"在整条链路上没有任何一处会报错。

静默兜底本身是对的（协议要求 `tag` 必填，抛错会让整个包生成失败），
但"兜底"和"告诉用户兜底了"是两件事，少后者就是把猜测伪装成事实。

现在打包**之前**就会显示：「有 N 个地点该地点标签暂缺，分享将使用默认标签
『休闲度假』」，并说明缺失原因是"照片刚导入时还没有描述文本"，
以及"不影响加密与验签"。
