# 阶段 9 · 轨迹回放（Trail Replay）

> **定位**：阶段 6「地图相册」的延伸能力，不是原定路线图阶段。
> 原图里的阶段 8 是「多 Agent 引用审计」（见 `docs/design/stage8-multi-agent-audit.md`，仍是提案），
> 本能力不占用那个编号，故编为 9。
>
> **一句话**：把"一堆带时间戳和坐标的照片"变成**一段能看下去的旅程**——
> 镜头跟着一个光点走，沿途照片一张张浮出来，底图是真地图。
>
> 现在的能力落在 `packages/trail/`（回放内核，与 React 无关），
> 由 `showcase/` 宿主（独立展示站，零后端依赖）。
> 主应用 `frontend/` 的接入尚未开始——所以严格说它目前只有"独立"这一种形态。

## 1. 这一阶段要解决什么

阶段 6 做完之后，"照片 → 时间/坐标 → 行程 → 地图 → 分享"这条链路已经通了，但**地图是静止的**：
所有照片一次性钉在图钉上，用户看到的是"一张有标记的地图"。

而"旅忆"这个词要的是**时间感**：那七天是怎么一天天过去的、从西宁出发一路向西。
静态地图给不了这个。所以要一条**可播放的轨迹**：光点按时间前进，镜头跟随，照片在抵达时浮出。

### 出口条件

| # | 条件 | 判据 |
| --- | --- | --- |
| 1 | 播放流畅 | **必须覆盖完整播放周期**（`tools/perf-timeline.mjs` / `verify-cards.mjs`）。结构性硬指标：所有窗口 **p50 ≤17ms** 且 fps ≥43；偶发软指标：p90>17ms 的窗口 ≤2 个、末窗口恢复、不连续 3 窗口长帧>10%。「只测 10 秒 ≥55fps」已作废 —— 结论完全取决于取在哪一段。判据为何分两层、五轮实测数据见 §6.4 补记 |
| 2 | 光点在画面中心附近 | 匀速播放时偏移 40~65px（这是相机的设计手感，不是越居中越好） |
| 3 | 照片能看见 | 播放中同屏 3~6 张，播完仍有 ≥3 张，互不遮挡文字 |
| 4 | 没有 Key 也能看 | 高德不可用时降级成示意格网，轨迹与播放不受影响 |
| 5 | 底图真的出图 | 播放 6 秒内瓦片请求 `ERR_ABORTED` ≈ 0（曾经是 293 次） |
| 6 | 全仓门禁 | `npm run typecheck && npm run test && npm run build` 全绿 |

## 2. 核心原理（先讲清楚再讲代码）

### 2.1 为什么不能"按照片一帧帧播"

照片是**离散**的：32 张照片、间隔几个小时到一天。直接按照片推进，画面会一顿一顿地跳。

所以要把离散点连成一条**连续的曲线**，再按"已经走过多少米"取样。

用一个比喻：把行程想成一根绳子，照片是绳子上的结。
- **Catmull-Rom 样条**：用相邻的结推出绳子该往哪个方向弯（保证过结时不打结）
- **等弧长重采样**：把绳子剪成 400 段等长的小段，每段记下"到起点多少米"
- **`samplePose(s)`**：给我"已经走了 s 米"，我告诉你此刻在哪、朝向哪、第几天

有了它，光点就能以恒定速度前进，而不是"在这张照片停 3 秒、再到下一张"。

> 💡 **向心（centripetal）参数化**：普通 Catmull-Rom 在两点距离差很大时会"甩出去"（过度弯曲）。
> 向心版本按距离的平方根加权，能消掉这个尖角。代码在 `packages/trail/src/spline.ts`。

### 2.2 为什么手算像素，而不是让地图自己画线

高德当然能画折线（`Polyline`），但我们需要的是一条**带发光、要走一段亮一段、还要跟着相机每帧重画**的线。
用 SDK 画，每帧改样式会触发它内部的重绘调度，拿不到 60fps。

所以：**底图归高德，轨迹归我们自己**。一块透明画布盖在底图上，我们用 Canvas 2D 画。

要把经纬度画到画布上，需要一步换算。Web 墨卡托的定义是：

```
整张世界地图 = 1×1 的正方形
lng → x：(lng + 180) / 360
lat → y：(1 - ln(tan(φ) + sec(φ)) / π) / 2       // φ 是弧度
屏幕像素 = 256 × 2^zoom × 墨卡托坐标
```

手算一个例子：zoom = 9.5 时，`256 × 2^9.5 = 185364`。
意思是"整个世界宽 185364 像素"，所以在北纬 37° 附近，1 像素约等于 170 米。
青甘环线 1738 公里 → 屏幕上约 10200 像素 → 1440 宽的屏幕装不下，必须跟镜头。

> ⚠️ **这条公式是精确的，不要"标定"**。我们曾经用 `map.lngLatToContainer()` 反推比例尺，
> 结果在地图还没加载完时读到了中间态，把误差永久烘焙进了投影。高德 2D 就是 EPSG:3857，
> `256 × 2^zoom` 和它逐位吻合——直接算。

### 2.3 「丝滑」的来源：相机晚半拍

如果每帧把地图中心设成光点位置，画面会**硬邦邦地锁死**，看起来像光点在拖地图。

真实的手持镜头会**慢半拍**。用一阶指数阻尼：

```
k = 1 - exp(-dt / τ)          // τ = 0.22 秒
相机 += (光点 - 相机) × k
```

`exp` 让这个系数**与帧率无关**——30fps 和 60fps 手感一致，这是固定系数（比如 0.1）做不到的。

匀速前进时，相机稳定落后一段距离。这段距离有解析解：

```
滞后(像素) = τ × 速度(像素/秒)
           = 0.22 × 237 ≈ 52 像素
```

**52px 就是这个演示的"手感"**，不是缺陷。所以验收标准是"40~65px"，不是"必须居中"。

> 🔍 这个数后来帮我们定位了一个大 bug：某次视口被压到只有 22 公里宽，
> 像素速度飙到 2680px/s，滞后变成 `0.22 × 2680 ≈ 590px`——
> 和实测的 571px 对上了，一次定位。

### 2.4 瓦片地图的死结：不能逐帧改中心

这是本项目最反直觉的一条。

高德的瓦片层在**每次视野变更时，会取消正在飞的瓦片请求**。逐帧 `setCenter`（60 次/秒）
= 每秒取消 60 次 —— 瓦片永远加载不完。实测：播放 6 秒，400 次请求、**293 次被取消**，
底图一片空白，只剩容器自带的 base64 占位底纹（看起来像"设计好的网格"，非常迷惑）。

解法不是"别动地图"，而是**分频**：

| 层 | 频率 | 谁在动 |
| --- | --- | --- |
| 我们的画布（轨迹/光点/卡片） | **60fps** | 每帧重算，绝对平滑 |
| 高德底图 | **25Hz**（40ms 一次） | 每步跳约 9.5px，肉眼几乎连续 |

关键在那句 `appliedMx / appliedMy`：**画布的投影锚定的是"地图上一次真正被设置的中心"，
不是相机当前值**。这样即使底图落后 40ms，轨迹和底图也永远对齐——落后的是底图，不是轨迹。

### 2.5 一条线要有"性格"：路段的交通工具

真实行程不是匀速直线：西宁到青海湖是自驾，嘉峪关到张掖坐高铁，景区里走走停停。
如果整条线一个样式，播放出来就是一根没有性格的线。

数据层很轻，只有两个字段：

- `Photo.transportToNext`：从这一张到下一张，用什么交通工具
- `Journey.segments`：首尾相接的路段数组，每段带 `startS / endS / mode`

视觉上**颜色和线型一起用**——深色底上只靠色相区分会糊掉：

| 交通工具 | 颜色 | 线型 | 直觉 |
| --- | --- | --- | --- |
| 自驾 | 青（主色） | 实线 | 默认、最"实" |
| 火车 | 琥珀 | 长虚线 `14 8` | 铁轨的节奏 |
| 飞机 | 淡紫 | 点线 `2 9` | 航线图上那种虚线 |
| 步行 | 浅绿 | 细点线 `3 5` | 慢、轻 |

**走过的路**仍是统一青色发光（那是这个应用的识别色），在上面叠一层细的交通工具色芯线；
**没走过的路**直接用各自的暗淡线型。于是播放时"前方是什么走法"一眼可见，
播完回看"哪段坐的什么"也留得住。

> ⚠️ **一条继承规则**：同一景点常连拍好几张，彼此只差 1km 出头。
> 短于 2000m 的路段**不单独成段、继承上一段**——否则整条线会被切出很多一小截的异色，
> 看起来像断点。这条规则由 `transport.test.ts` 的「同一地点的连拍不单独成段」守着。

> 🎯 **演示数据里有一处故意的失真**：青甘线「大柴旦翡翠湖 → 当金山口」标成了飞机，
> 只为让人看到第四种线型（点线·淡紫）。真实行程那 400 公里是戈壁公路，应该是自驾。
> 代码里有注释写明，不要照抄成"真实攻略"。

## 3. 逐块讲解

### 3.1 坐标与几何 —— `packages/geo/`

| 文件 | 内容 |
| --- | --- |
| `coords.ts` | WGS84 ↔ GCJ-02、境外判定 |
| `mercator.ts` | 墨卡托正反变换 |
| `distance.ts` | 球面距离（haversine） |
| `number.ts` | 夹取（含 NaN 兜底） |

**为什么单独成包**：这套转换一度在仓库里存在三份（后端 Python、主应用、展示站），
其中展示站那份把"境外判定框"抄窄了（`73.66~135.05` vs 标准 `72.004~137.8347`），
导致黑龙江东部、漠河一带的照片在两个应用里落到不同位置。合并后它是前端唯一入口，
`PROJECT.md` 第 10 条把它定成红线。

> 💡 为什么里程必须用球面距离而不是墨卡托平面距离：墨卡托在高纬会把东西向距离放大
> `1/cos(lat)` 倍。同样 1 度经度，赤道 111km、北纬 60° 只有 55.6km。
> `packages/geo/src/geo.test.ts` 里有一条对照断言专门守这件事。

### 3.2 样条与里程 —— `packages/trail/src/spline.ts`、`journey.ts`

- `spline.ts`：向心 Catmull-Rom 求值 + 等弧长重采样（400 点）
- `journey.ts`：把 `Photo[]` 变成 `Journey`（轨迹点、里程表、天数分组、站点）

`Journey` 里有三个关键数组：`trackMX/trackMY`（墨卡托坐标）、`trackS`（累计里程）、`trackT`（时间）。
另外 `photoS`（每张照片在轨迹上的里程位置）是给时间轴画刻度用的。

> ⚠️ **同一个景点的照片要去重成"一个站点"**。演示数据里同一景点的两张照片坐标抖动约 1.3km，
> 若按 50m 去重，16 个景点会被算成 32 个站，站距中位数从 150km 塌到 1km，
> 算出来的缩放级别会顶到上限——一个 bug 同时毁掉画面三件事。现在阈值是 2000m。

### 3.3 投影 —— `packages/trail/src/projection.ts`

一个极简对象：

```ts
{ cx, cy,       // 相机中心的墨卡托坐标
  ox, oy,       // 相机中心投射到屏幕的像素位置（一般是画面中心）
  scaleX, scaleY }  // 每墨卡托单位多少像素 = 256 × 2^zoom
```

`projectX(proj, mx) = ox + (mx - cx) × scaleX`。

只用一个 `setCamera()` 改 `cx/cy/ox/oy`，**缩放不变**（因为播放中不改 zoom）。

### 3.4 相机 —— `packages/trail/src/camera.ts`

34 行。`follow(target, dt, tau)` 做指数阻尼。
`tau` 由调用方按倍速缩放：`DEFAULT_TAU / max(1, speed)`。
4x 时压缩滞后（否则会甩到 208px），0.5x 时保持 26px（慢放是"看清细节"，镜头该更贴）。

### 3.5 时钟 —— `packages/trail/src/clock.ts`

持有 `q ∈ [0,1]`（进度）、`playing`、`speed`。
`tick(dt)` 推进，`seek(q)` 拖拽跳转，`replay()` 回到起点。

**它是整个动画的唯一时间源**。渲染、HUD、卡片、时间轴全读它，不各自计时。

### 3.6 渲染器 —— `packages/trail/src/renderer.ts`

Canvas 2D。每帧顺序：

```
清屏 → （降级时）画经纬格网 → 画未走过的虚线 → 画已走过的三遍描边（发光）
     → 叠交通工具色芯线 → 画站点圆点 → 画引线 → 画光点光晕 → 画暗角 → 画扫描线
```

「未走过的虚线」不是一整条：它按 `Journey.segments` 切开，每段用自己的颜色与线型。
切段时要注意**在段边界把上一个点补进新路径**，否则每跨一段就会出现一个采样间隔的缺口
（400 个采样点铺 1700 公里，一个采样点约 4 公里，肉眼能看见）。

三条性能红线，每条都对应一个真实掉帧原因：
1. **发光不用 `shadowBlur`**（每帧几十次高斯模糊），改成同一 `Path2D` 描三遍（10px/4px/1.6px）
2. **渐变与 pattern 全部缓存**，光晕用 `translate` 复用同一个渐变，不每帧 `createRadialGradient`
3. **轨迹点存 `Float32Array`**，绘制时直接算屏幕坐标，不生成对象数组；屏幕外 200px 剔除

### 3.7 底图适配 —— `showcase/src/map/baseMap.ts`

- `loadAmap()`：动态插 `<script>`，超时 / 重试 / 复用已加载的全局对象
- `createAmapController()`：`setCenter(lng, lat, true)`、`whenReady()`、`setStatus` 开关交互
- `createFallbackController()`：**没有 Key 时自绘可拖拽的格网**，否则"手工补地点"这条链路直接死掉

> ⚠️ `setCenter(center, immediately)` 第二个参数默认 `false` = 开内部过渡动画。
> 逐帧调用会变成"每帧新起一个 tween 互相打架"。必须传 `true`。

### 3.8 卡片 / HUD / 时间轴 —— `showcase/src/ui/`

- `PhotoCards.tsx`：每帧只写 `style.transform` / `style.opacity`，`display` 只在可见性翻转时改
- `Hud.tsx`：全部走 ref 写 `textContent`，且带值缓存（数字不变就不碰 DOM）
- `Timeline.tsx`：canvas 画刻度，指针捕获 + `lostpointercapture` 兜底

卡片布局是三遍处理：

```
计算可见性（名次窗口 / 停留 / 淡走）
  → 黄金角散布 → 避让光点 → 夹进安全区
  → 同屏密度截断（≤5 张，留离光点最近的）
  → 3 轮成对分离（每轮后重新夹取）→ 最终避让 → 最终夹取
```

### 3.9 主循环 —— `showcase/src/App.tsx`

一个 `requestAnimationFrame`，一帧做九件事，**全程零 `setState`**（唯一一次在播放状态翻转那帧）：

```
clock.tick(dt)
samplePose(journey, q × 总里程)      → pose
camera.follow(pose, dt, tau)         → 相机
（若距上次下发 >40ms 且位移 >2px）controller.setCenter(...)  → 推底图
setCamera(proj, appliedMx, appliedMy) → 对齐画布与底图
cards.update(...) / renderer.draw(...) / hud.update(...) / timeline.draw(...)
```

**依赖方向单向**：`宿主（frontend / showcase） → @travelmemory/trail → @travelmemory/geo`。
内核不认识 React，也不知道自己有哪个宿主——这是它能被两套完全不同的界面复用的原因。

## 6. 踩过的坑（这一节最值钱）

### 6.1 八个真 bug

| # | 症状 | 根因 | 一个数字定位 |
| --- | --- | --- | --- |
| 1 | 光点偏 570px、卡片全在屏外、底图空白 | `suggestedZoom` 顶到 13（应为 9.5）：站点去重阈值 50m < 照片抖动 1.3km | 视口 22km；像素速度 2680px/s；`0.22 × 2680 ≈ 590px` |
| 2 | 轨迹只剩左上角一小块 | `.play-canvas` 没有 `width/height`，canvas 作为替换元素按固有尺寸 300×150 解析；`resize()` 又把属性写回自身，自锁 | `renderer.width = 300`、`proj.ox = 150` |
| 3 | 播完 4 秒后屏幕一张卡片都没有 | `crossedOnce` 一旦为真不复位，`reveal` 在 3820ms 后恒为 0 | `REVEAL 320 + LINGER 2600 + FADE 900 = 3820` |
| 4 | 播放时底图一片空白 | 逐帧 `setCenter` 取消在飞的瓦片请求 | 6 秒 400 请求 / **293 aborted** |

| 6 | 进度条键盘完全用不了（P2 无障碍） | 只有 `role="slider"` + `tabIndex={0}`，没有 `onKeyDown`：读屏用户能聚焦、按什么都没反应 | 已补 Arrow/PageUp/PageDown/Home/End + Shift 精调 + `aria-valuetext`；键位映射抽成 `sliderStep` 纯函数，7 条回归测试 + 真机键盘复验守着 |
| 7 | 播放后段稳定掉到 46fps、p90 32.8ms | `Timeline.draw()` 每帧在写完卡片样式后调 `getBoundingClientRect()`，强制同步重排吃光帧预算，让每 3 帧一次的 `setCenter` 一顶就过线 | CPU profile 定位（329ms/10s）；尺寸测量搬进 `ResizeObserver` 缓存，p90 降到 16.5ms、长帧率 30–50% → ≤7%；契约测试 4 条守着，详见 §6.4 第五步 |
| 8 | 主应用配了高德安全密钥却不生效 | 两份加载器各写一份，`frontend/amap.ts` 写成 `window._AMapSecurityConfig = { securityCode }`；高德官方字段是 **`securityJsCode`**（JS API 2.0 安全密钥文档），展示站那份写对了 | 抽 `packages/amap-loader` 统一机制（14 条测试含字段名回归）；三处地图真机验到 `config=["securityJsCode"]`、0 报错。**复制两份代码漂移出来的真 bug** |

### 6.2 四条方法论错误（比 bug 更值得记）

1. **测试的验收区间不能取实现的 clamp 区间**。
   `clamp(x, 7.5, 13) ∈ [7.5, 13]` 是恒等式，不是断言行为。原测试两端恒真，
   于是 96 条全绿而画面全废。

2. **`environment: 'node'` 没有布局引擎**，`getBoundingClientRect()` 不存在。
   单测全绿与"渲染全废"可以同时成立 —— **浏览器截图必须是 P0 门禁**。

3. **判据要与观察模型匹配**：
   - 用 `className="…block…"` 判断 Tailwind 污染来源 → 错（Tailwind 是对文件**全文分词**）
   - 用 `grep 压缩后标识符` 数出现次数 → 错（minifier 会改名）
   - 用"画布角落像素 alpha"判断有没有格网 → 错（暗角渐变让全画布 alpha 恒在 100~140）
   - 可靠的只有：CSS 选择器文本、用户可见字符串、或直接目视裁切图

4. **断言要能红才算回归测试**。写完先拿旧实现跑一遍，确认它会失败。
   「近似重复照片不变性」那条之所以有用，是因为它在旧代码上 `Δ = 5.0`（8.0 → 13.0）。

### 6.3 两个"看起来是 bug，其实不是"

- **光点不在正中心**：设计如此。`τ × v` 的稳态滞后就是 52px，是"手持镜头"的手感。
- **播放时看不到 POI 地名**：高德在连续视野变更时对标签层降级，非我们可控。
  暂停 2 秒后地名成片出现。任何缓解（降低刷新频率）都会把瓦片压力推回去，不值得。

### 6.4 帧率调查：一次把结论推翻重来的过程

这一节记的是**一条结论被推翻了三次、最后才找到真凶**的全过程。
后来人要动播放主循环之前，请先读完它 —— 尤其是「第五步」，它推翻了前四步的结论。

#### 起因：一个看起来很合理的推理

验收报了两个数：主应用回放 43.8fps，展示站 59fps，同一台机器。于是很自然地得出
"两者共享同一份回放内核，却差 15 帧，主应用背后一定压着什么结构性负担"。
后面好几轮调参（去掉毛玻璃、改 `setCenter` 间隔、卸载背后那张地图）都建立在这句话上。

#### 第一步：先给秒表本身校准

我没接着调代码，而是先搭了一条独立的测量链路：Edge 157 无头（真 GPU，ANGLE / Intel Iris Xe）
+ CDP 页面内 rAF 采样，脚本见 `tools/perf-timeline.mjs`（自带启动预览服务和浏览器，跑完自己清理）。

先测一个**什么都没画**的空页面：61.1fps / p50 16.4ms / 长帧 0%。
秒表是准的，接下来量出来的数字才可信。

然后用同一把秒表打展示站，6 秒一窗连采 10 窗：

| 时间 | 进度 | fps | p90 | 长帧率 |
| --- | --- | --- | --- | --- |
| 6–24s | 15%→58% | 55–61 | 16.5 | 0.5–3% |
| 30s | 70% | 47.3 | 16.5 | 3.8% |
| 36–42s | 84%→96% | 46.0 | **32.8** | 32% |
| 48s | 100% | 46.5 | 16.5 | 6.2% |
| **54–60s** | **100%（已播完）** | **61.1** | **16.4** | **0%** |

**展示站自己就只有 41–45fps。** 于是当时断定「差 15 帧」不存在（**这一步只对了一半**）：
后来第五步实测主应用回放层全程 53.8–61.2fps，说明两边**确实有差距**，
只是方向和原来报的正好相反 —— 慢的是展示站，不是主应用。
不过方法上的教训仍然成立：拿两个不同时刻的瞬时值当"A 与 B 的差距"，
等于拿一个人跑步时和坐下时的心率证明他心脏有问题；帧率在这条链路上会随
瓦片缓存状态在 34–61fps 之间漂，任何单点数字都不能当结论。

#### 第二步：40ms 和 50ms 其实是同一个数

`lastCenterAt = now` 里的 `now` 是 rAF 时间戳，相邻帧恒差 16.667ms，所以间隔会被
**量化成整数帧**：

```
ceil(40 / 16.667) = 3 帧
ceil(50 / 16.667) = 3 帧   ← 而且 16.667 × 3 = 50.0000，正好压在临界点，真假各半
```

所以那次"40 → 50 把重排摊薄一点"的改动，在算术上是**恒等变换**，还额外引入了
3~4 帧之间的抖动。每 N 帧被顶掉一帧的理论上限是 `fps = 60·N/(N+1)`，
N=3 → 45fps，正好对上实测的 46fps 和 32% 长帧率。

#### 第三步：三次归因实验，排除了内核，但结论下早了

1. **屏蔽绘制项**（不改源码，页面里临时让某些绘制变空操作）：
   `base 59.8 → noFull 57.4 → noCanvas 59.2 → base 45.3`。
   看着像"屏蔽有效"，其实是**采样时刻越来越晚**。同一页最后再测一次 base 就掉回 45.3。
   这个实验真正的价值是暴露了"帧率随时间变"，不是证明哪个绘制项有罪。

2. **试着把渲染器定罪**：三次全屏 pass（清屏 / 暗角径向渐变 / 扫描线）、每帧重建
   Path2D、已走过段描四遍……读代码能列出一堆嫌疑。但上表最后两行是反证：
   **播完之后已走过段是全量（理论上最贵），却满血 61fps**。

3. **怕"播完就不画了"让采样器空转**，于是数了每秒 `clearRect` 次数：
   全程 44–62 次/秒，播完之后仍是 61 次/秒，每帧约 32 次描边恒定。
   **主循环和 `renderer.draw()` 一刻没停**。渲染器清白，画布不是瓶颈
   （另测 `stroke` 每帧仅 0.36ms）。

当时下的结论是「掉帧是外部事件（高德瓦片加载），跟我们无关」——**这个结论后来被推翻了**，
见第五步。这三次实验真正证明的只有一件事：**`packages/trail` 的渲染器是清白的**，
瓶颈在宿主层。把「内核无罪」误推成「我们无罪」，是这一轮最值得记的思维跳跃。

#### 第四步：一个无效方案，以及为什么把它删了

按"少调几次 `setCenter` 就少几次重排"的思路，试过把间隔放到 100ms（6 帧），
并且为了不让底图看起来一跳一跳，中间几帧用 CSS `transform` 把地图容器补平移
（容器四边外扩 80px 留余量，比例尺由 zoom 决定、与容器尺寸无关，投影不会歪）。
想法很完整，实测：

| 时间 | 改前（40ms） | 改后（100ms + transform） |
| --- | --- | --- |
| 36s | 46.0 | **34.8** |
| 42s | 46.0 | 47.1 |
| 48s | 46.5 | 47.9 |

没有收益，局部更差。原因大概是间隔拉长后瓦片请求更集中、一次要铺的面积更大。
**已完整回退**，两处宿主的 `CENTER_INTERVAL_MS` 统一回 40。
留着这个改动只会让代码变复杂、还让人误以为帧率被修好了。

#### 第五步：接力复验，把结论再推翻一次

队友那轮因额度中断，欠下三件真机验证：主应用回放层的帧率、键盘无障碍、主线程归因。
补做之后，前面的结论整个翻了过来。

**① 主应用回放层根本不慢。** 后端要 Postgres、库又是空的，所以没去折腾数据库，
而是在浏览器层用 CDP 的 Fetch 域拦下 `/api/v1/trips`、`/api/v1/photos`，喂一份与展示站
同站点、同 32 张照片的青甘假数据（`tools/verify-replay.mjs`，不碰后端、不改产品代码）。
同一台机器、同一把秒表，采完整播放周期：

| 时间 | 5s | 10s | 15s | 20s | 25s | 30s | 35s | 40s | 45s |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 进度 | 21% | 35% | 48% | 62% | 76% | 88% | 100% | 100% | 100% |
| fps | 61.2 | 61.1 | 57.3 | 60.5 | 61.1 | 53.8 | 61.1 | 61.1 | 57.7 |
| p90 | 16.5 | 16.5 | 16.5 | 16.5 | 16.5 | 16.5 | 16.5 | 16.6 | 16.6 |
| 长帧率% | 0 | 0 | 3.1 | 0.3 | 0 | 0.7 | 0 | 0 | 0.7 |

**全程 53.8–61.2fps，p90 恒 16.5ms。** 所以「两应用同水位」是错的：共享内核、同坐标、
同机器，快的一方恰好证明内核没问题，慢的一方一定有自己的额外开销。

**② CPU profile 点名了那笔开销。** 同一次播放的前段（3–13s，61.1fps）与后段
（30–40s，56.5fps）各抓 10 秒 V8 CPU profile（`tools/profile-replay.mjs`），
按函数聚合 self time，后段比前段多出来的前几项：

| 增量 | 前段 → 后段 | 函数 |
| --- | --- | --- |
| +145.9ms | 775 → 921 | `(program)` |
| **+94.1ms** | 234 → 329 | **`getBoundingClientRect`** |
| +68.2ms | 31 → 99 | `vertexAttribPointer`（高德 WebGL 瓦片） |
| +63.7ms | 54 → 118 | `e.set`（高德内部） |
| +59.0ms | 105 → 164 | `e.Tn`（高德内部） |
| +29.3 / +21.3ms | — | `stroke` / `lineTo`（canvas 2D） |

`getBoundingClientRect` 10 秒里吃掉 329ms，而且是**每帧**发生。顺着它找到
`showcase/src/ui/Timeline.tsx` 的 `draw(q)`：主循环每帧先写完 32 张照片卡片的
`style.transform/opacity` 和 HUD 文本，紧接着时间轴就调它量宽度 —— **写完样式立刻读几何**，
浏览器被迫同步重排一次（layout thrashing）。主应用回放层没有时间轴，所以没这笔开销。

**③ 修掉它，两轮复测都好了。** 尺寸测量搬进 `ResizeObserver`（挂载 / 尺寸变化时量一次，
缓存 `width` 与 `dpr`），`draw()` 每帧只读缓存数字，首帧回调未到时跳过一帧。
契约测试 `showcase/src/timeline.test.ts` 锁住「draw 里不准出现 getBoundingClientRect」，
时间轴 backing 全程 1134×68（确认没把画布修停摆）。

| | 修复前（多次记录） | 修复后 轮1 | 修复后 轮2 |
| --- | --- | --- | --- |
| fps 区间 | 34.8–61.1，后段稳定 46 | 49.5–61.1 | 54.8–61.1 |
| p90 | 后段恒 **32.8ms** | 16.5–16.8 | 16.5–16.6 |
| 长帧率 | 30–50% | ≤6.9% | ≤2% |

**p90 是这里最硬的指标**：32.8ms 正好是两帧，代表「每 3 帧丢 1 帧」的结构性掉帧；
降到 16.5ms 说明这个结构消失了，而不只是平均值被偶发尖峰拉来拉去。

#### 真正的因果链

`setCenter` 每 3 帧一次重排（40/50ms 都量化成 3 帧）本来就在帧预算边缘，
时间轴又每帧强制重排把余量吃光，于是那一帧一顶就过 16.7ms。
工程师早先判断「不是事件太重，是余量不够」完全正确，只是找错了吃余量的那一项
（他猜三次全屏渐变，实际是每帧一次强制布局）。这也解释了为什么降 `setCenter`
频率、屏蔽渐变都没用 —— **动的是分子，问题在分母**。

顺带把键盘也真机验了：`tools/verify-replay.mjs` 用真实 `Input.dispatchKeyEvent` 派发，
Home / ArrowRight / Shift+Right（+1%）/ PageUp（+10%）/ End / 到头不越界 / 字符键不拦，
`aria-valuenow` 与 `aria-valuetext`（`第 7 天 · 100%`）同步，Esc 关闭并释放焦点，全 PASS。

时间轴改成 ResizeObserver 后也复验了交互：canvas backing 1134×68，点击轨道物理 75% 处
进度从 0% 跳到 78～79% —— 与 `qFromClientX` 的 `PAD = 56` 留白模型算出来的 77.7% 吻合，
说明 `getBoundingClientRect` 只在「指针事件」里保留是对的（那不是每帧路径）。
顺带又撞了一次 §6.2 的老坑：第一次判据写成「期望 75%」且用 `Number('78%')` 比较，
结果是 NaN 直接判 FAIL —— **判据必须和观察模型匹配**，不是功能坏了。

#### 补记：把照片卡片接进主应用后的复验

后来把展示站那套照片卡片移植到了主应用回放层（`replay/PhotoCards.tsx`），
并从 IndexedDB 接通了真实缩略图（`replay/thumbs.ts`）。这事本身不难：
`PhotoCards` 的 TS 层只 import 共享包，内核的 `Photo.thumb` / `anchors` /
`drawLeaders` 早就齐备，后端零改动（原图永不上云，缩略图是导入时前端生成、
按 photoId 存本机缓存的）。

**接法上守了两条**：
- 缩略图返回 `photoId → objectURL` 映射交给组件，**不改 `Journey`、不改 adapter**。
  `buildReplayJourney` 是同步纯函数、又是主循环 effect 的依赖，改成 async 或重建
  journey 都会把播放打回 0%。映射只触发一次 React 重渲染，主循环毫发无伤。
- CSS 全部限定在 `.replay-root` 下，且**去掉了 `backdrop-filter`**、不引用主应用
  浅色主题的 `--text`（会变成深底深字）。契约测试 `photoCards.test.ts` 锁住
  「`update()` 和 `frame()` 里都不准出现布局读取 API」—— R1 那条唯一能把
  32.8ms 请回来的路径。

真机验收 `tools/verify-cards.mjs` 覆盖四件事：32 张卡片渲染（同屏 ≤5）、
完整播放周期帧率、键盘/Esc 回归、往 IndexedDB 塞一张真 JPEG 后重开看卡片背景
变成 `blob:` URL。前三项之外的帧率，连跑五轮：

| 轮次 | fps 区间 | p50 | 说明 |
| --- | --- | --- | --- |
| ① 紧接 build | 29.9–39.8 | **32.7 全程** | 冷启动异常，后续四轮未复现 |
| ② `--diag` 四组 | 58.8–61.1 | 16.4 | 逐项屏蔽卡片渲染，四组几乎无差别 |
| ③ | 43.1–61.1 | 16.4 | 90–100% 两个窗口 p90 32.8，之后恢复 |
| ④ | 52.2–61.2 | 16.4 | 全绿 |
| ⑤ | 51.6–61.2 | 16.4 | 全绿 |

**p50 在 4/5 轮恒为 16.4ms**，与接卡片之前的基线（53.8–61.2fps / p90 16.5ms）
同水位 —— 卡片没有引入结构性回归。第 ③ 轮的后段尖峰是瓦片首次加载，
第 ① 轮连 p50 都变成 32.7 则是一次没复现的冷启动异常。

于是把验收判据改成**两层**，而不是挑一轮好看的数据蒙过去：

- **结构性（硬）**：所有窗口 `p50 ≤17ms` 且 `fps ≥43`。这一条直接排除
  「每帧都慢」—— Timeline 那个坑正是 p50=32.7。
- **偶发（软）**：`p90 >17ms` 的窗口 ≤2 个、最后一个窗口必须恢复、
  不允许连续 3 个窗口长帧率 >10%。

只看「每窗口 p90 ≤17」会把瓦片冷启动噪声误判成代码回归；只看平均 fps 又会
放过结构性掉帧。两者都不是好尺子。

顺带又踩了一次判据坑：验证缩略图时写 `/url\(blob:/`，实际浏览器把内容规范化成
`url("blob:...")`（多了一对引号），功能明明是通的却判 FAIL。**判据必须匹配
观察模型**，这条在 §6.2 已经写过，这里再犯一次，记下来免得第三次。

#### 现在的状态与验收口径

- 展示站：全程 ≥49.5fps、多数 ≥54fps，p90 ≤16.8ms，长帧率 ≤7%。
- 主应用回放层：全程 53.8–61.2fps，p90 恒 16.5ms。
- 仍有偶发尖峰（p99 到过 65ms），来自瓦片首次加载，属可接受。

**验收口径**（用 `tools/perf-timeline.mjs` 采完整播放周期）：
单窗口最低 ≥49fps；**p90 ≤17ms**；长帧率 ≤10%；无连续 3 帧以上长帧。
比原先「随便测 10 秒 ≥55fps」严格，因为它同时约束平均值和分布形状。

#### 这一节沉淀的方法

1. **先校准测量工具**，再解释测出来的数（空页面 61.1fps 是这条链路的"零点"）。
2. **别把时间序列上的两个点当成两组对照**；要么同时测，要么画出整条曲线。
3. **读代码能给出频率和恒等式，给不出毫秒数**；反之测量能给出数字，给不出归因。
   两边都要有，且要互相证伪。
4. **改动没收益就回退**，哪怕它写得很漂亮、注释很完整。
5. **「内核无罪」不等于「我们无罪」**：共享内核在 A 宿主跑满帧，恰恰说明 B 宿主
   有自己的问题。找一个「同样输入但更快」的对照，比在慢的那边继续调参有效得多。
6. **看 p90 而不只看平均 fps**：平均值会被偶发尖峰拖着走，p90 才能区分
   「结构性丢帧」（32.8ms）和「偶发毛刺」（p50/p90 都 16.5ms）。
7. **一次运行的帧率不可复现时，先怀疑测量条件**（这里是瓦片缓存状态），
   别急着给它编一个结构性解释。接卡片后的五轮里就出现了一轮 p50=32.7 的冷启动异常。
8. **用分布形状而不是单点数字当判据**：`p50` 判结构性、`p90` 判偶发尖峰、
   平均值只作参考。只盯一个数，不是把噪声当成回归，就是把回归当成噪声。

## 7. 动手练习

1. **改手感**：把 `camera.ts` 的 `DEFAULT_TAU` 从 0.22 改成 0.5，观察光点滞后变大、画面变"飘"。
   再改成 0.05，会变成硬锁死。体会"丝滑"是**滞后**带来的，不是"更快"带来的。
2. **改速度**：`data/demoJourneys.ts` 里把行程时长减半，注意 `CENTER_INTERVAL_MS` 是否还够——
   速度翻倍会让底图每步的跳动从 9.5px 变成 19px。
3. **复现坑 1**：把 `journey.ts` 的 `STATION_MERGE_METERS` 改回 50，跑 `npm test`，
   看 `demo.test.ts` 的 zoom 区间断言怎么红。
4. **复现坑 3**：把 `PhotoCards.tsx` 里 `Math.max(reveal, paused && rankNear ? dim : 0)`
   改回 `reveal`，播完等 5 秒，屏幕上会一张卡片都不剩。
5. **改交通工具**：把 `demoJourneys.ts` 里青甘某一段的 `mode` 从 `drive` 改成 `flight`，
   播放时那一段会变成淡紫点线。再把 `transport.ts` 里的 `dash` 改成 `[30, 2]`，
   体会"线型比颜色更容易被看见"。
6. **复现坑 7**：把 `Timeline.tsx` 的 `draw()` 里 `const { width, dpr } = sizeRef.current;`
   改回 `const rect = canvas.getBoundingClientRect(); const width = Math.round(rect.width);`，
   先跑 `npm test --workspace=travelmemory-showcase` 看契约测试怎么红，
   再 build 跑 `tools/perf-timeline.mjs`，看后段 p90 怎么从 16.5ms 回到 32.8ms。
   这个练习最能体会「一行读布局的代价」。
