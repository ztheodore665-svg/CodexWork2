# 阶段 6 · 地图相册 + 跨端 + 隐私分享（W6-1 ~ W6-5）

> 这一阶段要解决什么：**把"照片 → 时间/坐标 → 行程 → 地图 → 分享出口"这条现实世界的链路接起来**，
> 并回答隐私分享的核心问题——"我把旅行记忆发给朋友，能不暴露原图和精确位置吗"。
> 答案分两半：坐标在服务端加噪（拉普拉斯），内容在用户设备上加密（定向信物）。

> `tsc --noEmit` 与 `vite build` 均通过。

## 2. 核心原理讲解

### 2.1 W6-1：时区为什么必须"双写"

照片 EXIF 里的拍摄时间有两个彼此不可替代的语义：

| 字段 | 写入 | 用途 |
| --- | --- | --- |
| `taken_at` | UTC，tz-aware | 索引排序、跨时区归并 |
| `taken_at_local` | 拍摄地当地时间，naive | **按天聚合只认它**——"第一天/第二天"是人类概念，不是 UTC 概念 |

只写 UTC 的后果：一张 10 月 1 日 01:30（UTC+8）拍的照片，UTC 是 9 月 30 日 17:30，
按 UTC 归会把它排进"前一天"，时间线整体错位一天。EXIF 的 `OffsetTimeOriginal` 就是干这个的；
没有时区信息时 `taken_at_local` 退化为 UTC 值并在 `tz_source` 里标记 `unknown`。

**去重按内容不按文件名**：`sha256(文件字节)`。同名不同图是两张，不同名同图（相机重复导出、
微信压缩转发）是一张——后者才是相册去重的真实场景。

**无 GPS 兜底**：`location_source='none'` + `location_confidence=0.0`。注意"没有坐标"和
"坐标不可信"是两回事，前者整条记录仍然有效（时间线照样排），只是不上地图。

### 2.2 W6-2：规则聚类为什么不用 DBSCAN

`trip_cluster.py` 只用两个人类可直觉判断的阈值：

```
时间断层：相邻两张照片 > 12h   → 切一刀（过夜会超，同日活动不会）
空间跳变：都有坐标时 > 50km    → 切一刀（同城移动远小于它，跨城高铁/航班远大于它）
```

DBSCAN 需要调 `eps`/`min_samples`，而 `eps` 在经纬度空间没有直觉含义（1 度 ≈ 111km 还是
≈ 85km 取决于纬度），调参过程不可解释、不可复现。本项目的 Trip 是**给人看的时间线**，
不是给模型的特征，阈值本身就是产品语义。

坐标缺失的照片只参与时间切断（`max_gap_km` 对它们不生效）——把"没坐标"当成"在原地"
会把一整段城市漫步错切成一个 Trip。

### 2.3 W6-3：接缝比实现重要

`types/native.ts` 先划接缝，`services/native/` 再填实现。三个刻意的取舍：

1. `takenAt`（UTC）与 `takenAtLocal` 分开——同 W6-1 的双写理由；
2. `coordSystem` 显式标注——高德用 GCJ-02、EXIF 是 WGS84，混用偏几百米；
3. `readThumb` 返回 `ArrayBuffer` 而不是 dataURL——原样进 IndexedDB 和 RPC body。

Web 实现拿不到 EXIF（`<input type="file">` 只给原始字节），**刻意不重复实现**：
照片的相机端解析一次（W6-1 后端），端侧再解析一次必然出现"相册显示 19:30、地图 20:00"。
Native 是明确的桩：调用即抛错，而不是静默返回空数组——最难查的失败形态是"看起来成功了"。

### 2.4 W6-4 后端：拉普拉斯模糊的三个决定

**① 服务端做，不做在前端。** 前端自己加噪也能"看起来一样"，但那样真实坐标和 ε 都留在
控制台里，隐私保证形同虚设。服务端每次只见**一个孤立点**（不是整条轨迹），只回加噪点——
它自己也无从还原轨迹，这是唯一能阻止"轨迹关联"的构造。

**② 每次独立抽样。** 同一坐标调用两次得到两个不同的点。若对同一坐标总返回同一结果，
外部重放几次就能校准出真实位置。

**③ `radius` 是承诺半径，不是实际偏移量。** 前端只知道"真实位置在以加噪点为圆心、
`radius` 为半径的圆内某处"，攻击者亦然。这是 ε-地理不可区分性标准的直接产物：
`b = radius / ε` 是拉普拉斯尺度，ε 越小圆越大。

**开关关闭返回 404 而不是 403**：未启用的能力对外表现为**不存在**。403 等于告诉外部
"这里确有此功能"，把未来的攻击面先画在地图上。

### 2.5 W6-4 前端：TrailShare 移植的密码学设计

从 TrailShare（协议 `ts-2026.4`，204 单测的零后端参考实现）移植，落在
`services/crypto/`（keys/sign/encrypt/commitment）与 `services/share/`（schema/filter/pack/unpack/prepare）。

**KEM + DEM，不是"给每个人加密一遍"**：

```
DEM：每组一把随机 32 字节组密钥，AES-GCM 加密照片与 meta（每张照片独立 12 字节 IV）
KEM：对每个收件人，临时 X25519 → ECDH → HKDF-SHA256 → 包一份组密钥
     盐 = sha256(ephPub ‖ recipientX25519Pub)  ← 防同一把 wrapKey 跨人复用
```

解封时逐个试 `wrappedKeys`，AES-GCM 解不开就是"不是给你的"——**不区分**"密钥错"和
"数据坏"，避免探测。一份 32 字节种子同时派生 Ed25519（签名）与 X25519（KEM）：
用户只需备份一个种子；老用户的 X25519 公钥由 Ed25519 公钥按 RFC 7748 标准转换现算。

**承诺覆盖什么、不覆盖什么**：

| 进承诺（公开） | 不进承诺（密文里） |
| --- | --- |
| 可见 place 的 `(placeId, tag, intensity)` + 每组盐 | 日期、地点名、label、配文、照片 |

不持钥的人也能验证"这个组里有几个地点、标签分别是什么、没被换过"，但看不到去了哪、
哪天去的。**屏蔽与承诺天然一致**：被取消勾选的条目不打包，承诺也覆盖不到。

**四条如实保留的边界**：

1. **屏蔽 = 不打包**，不是"打包后隐藏"——但文件大小仍泄露"这次内容不多"；
2. `tag`/`intensity` 明文——承诺可验证的代价；
3. 界面从不报总数——`unpackForViewer` 不返回 `pkg`，UI 拿不到组数；
4. **传播边界是文件级**：防得住"转发给未授权的人打不开"，防不住"授权用户截图"。
   这不是 DRM，是信封。

**私钥红线（PROJECT.md §二、[9]）**：解密私钥只在设备本地生成，只写 `localStorage`，
`services/crypto` 与 `share` 全链路没有任何网络调用（网络只在 `api/privacy.ts` 一个文件里，
且它只收/发坐标）。换设备 = 换身份，种子备份列为 Future Work。

### 2.6 融合打包：`prepare.ts` 一个文件装下全部差异

`pack()` 保持规范原样（不知道坐标、不发请求）。TravelMemory 特有的"先模糊再打包"
被压缩在 `prepare.ts`：

- 只对**可见** place 调模糊——遍历整个 Trip 会向服务端暴露"用户其实去了哪"，
  屏蔽语义会被旁路绕过；
- 每个地点单独 try/catch：失败 → 不写坐标 + 一条 warning，**打包照常成功**；
- 绝不能"模糊失败就用原坐标"——那等于静默分享精确位置；
- 模糊函数由调用方注入——`share/*` 保持"不碰网络"的分层边界，单测注入假的。

地图渲染规则（`pages/MapPage/layers.ts`，纯函数 + 单测）：

| PlaceMeta | 渲染 |
| --- | --- |
| `radius > 0` | `Circle` 半透明圆（18% 填充），**不画 Marker** |
| `radius` 缺省/0 | `Marker` |
| 无坐标 | 不上地图 |

WGS84 → GCJ-02 在前端按与后端 `app/utils/coords.py` **逐位同构**的方式重写一遍
（同一组常数、同一组公式、同一个天安门测试向量）。为每个点回后端转坐标意味着地图每帧
一堆 HTTP 请求，不可接受；两端对不上比任何一侧"看起来对"都严重，所以用测试向量锁死。

### 2.7 W6-5：退化守护

`test_degradation.py` 把"阶段 6 四个开关（`photo_import`/`map_album`/`native_bridge`/`privacy`）
全关"定义为**阶段 5 行为**，断言此时主流程指标（Recall@5、引用率、拒答正确率）与开关存在前
完全一致。扩展模块走 feature flag 且默认全关（PROJECT.md §二、[8]），这条测试是
"扩展代码合入 main 的前提"的可执行形式。

## 4. 人工验证清单（**尚未执行**，留给人类）

自动化覆盖了协议、密码学与纯逻辑；以下必须真机/双窗口手验：

1. **双窗口收发**：两个独立无痕窗口（Ctrl+Shift+N 两次，同窗口两个标签共享 IndexedDB
   = 同一个人），互加公钥 → 生成 → 导入 → 只有收件人解得开。
2. **模糊圈渲染**：导入带坐标的信物 → 地图上半透明圆（半径 = 承诺半径）；无坐标地点不显圈。
   高德 key 已在 `frontend/.env.local`（来自根 `.env` 的 `AMAP_JS_KEY`）。
3. **降级路径**：后端 `privacy` 开关关掉（或断网）后重新生成 → 打包仍成功，地点无坐标，
   有 warning。**任何情况下不允许退化成"发原坐标"**。
4. **W6-1 导入性能**：1000 张导入 + 打标 + 索引 < 10 分钟（出口条件）。
5. **W6-2 渲染性能**：1 万点 ≥ 60fps——组件按骨架交付，聚合/裁剪调优留待真机数据。
6. **Android 真机**：Capacitor 壳 + 相册权限 + 导入→成图→问答（W6-3 出口条件）。

## 5. 已知局限与 Future Work

| 局限 | 说明 |
| --- | --- |
| 信物 UI 是骨架 | 旅程编辑器、可见性勾选树、好友名单、接受/拒绝落记忆均未做（TrailShare 规范 §8 完整 UI）；示例旅程内置在 `demoTrip.ts` |
| 照片图层无数据源 | 后端暂无照片列表 API；`layers.ts` 的 `source:'photo'` 分支与开关已就位，接上即用 |
| 文件大小侧信道 | 屏蔽 = 不打包，包体积随可见内容变化 |
| 公钥无验证机制 | 手工交换的公钥若被替换，会加密给错误的人且全部"验证通过"；生产需带外核验（二维码/长指纹） |
| 身份不能导出 | 清站点数据 = 换身份，之前的信物全部打不开；种子备份（助记词）列为 Future Work |
| 旧版信物不兼容 | v2026.3 及更早一律拒绝，无迁移层 |
| 语义感知扰动 / ZK | 阶段 7 科研轨，本章 §8.6 保留原设计 |
| 高德 key 在前端产物 | JS key 设计上浏览器公开（referer 白名单保护），但任何人可读；勿当机密 |
