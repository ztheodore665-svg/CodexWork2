## 0. 一句话

> **同一份旅行记忆，三档执行：本机能答的本机答，需要措辞的只发选中的几条，需要综合的才上传索引——每一档都给你一张小票。**

这句话同时回答了三个问题：产品是什么、技术差异在哪、凭什么让人信。

---

## 1. 先诊断：两个项目为什么现在拼不成一个产品

| # | 现象 | 后果 |
| --- | --- | --- |
| 1 | 主项目是**服务端 RAG**（FastAPI + Postgres + pgvector），产品叙事却要说"本地优先" | 演示时一讲架构就自相矛盾：嘴上本地，数据在云 |
| 2 | TrailShare 是**完整但孤立**的产品（零后端、加密信物、规则推荐），只覆盖"六类标签推荐" | 接不回主项目，只能当"另一个作业"并列展示 |
| 3 | 主项目功能很多（RAG/记忆/工具/评测/隐私/语义推荐），但**没有一个用户能复述的价值主张** | 答辩时评委记不住，面试时讲不清 |

**不是功能不够，是缺一条能把两套代码串起来的主线。**

## 2. 主线：三档阶梯（L0 / L1 / L2）

```
用户提问
   │
   ├─ L0 本机档 ── 本机检索 + 本机规则生成 ── 0 条上传
   │     覆盖：枚举、计数、时间、地点、标签统计
   │     证据：本机照片 + 朋友信物
   │
   ├─ L1 薄引擎 ── 本机检索 + 云端无状态生成 ── 只发选中的 K 条
   │     覆盖：需要措辞/归纳，但证据面窄的问题
   │     服务端不留存，请求结束即忘
   │
   └─ L2 全引擎 ── 云端检索 + 云端生成 ── 上传派生索引（TTL）
         覆盖：跨行程综合、语义模糊、需要重排的问题
         原图与精确坐标永不参与
```

| 档位 | 检索在哪 | 生成在哪 | 外发什么 | 留存 | 典型问题 |
| --- | --- | --- | --- | --- | --- |
| **L0** | 本机 IndexedDB | 本机规则（无模型） | 无 | 无 | "去年秋天去了哪些古镇？""一共几个城市？""我在杭州偏好哪类地方？" |
| **L1** | 本机结构化 + 词面 | 云端 LLM，无状态 | 选中的 K 条日文档（K ≤ 8） | 请求结束即忘 | "这趟和上次那趟像在哪？""用三句话总结这次旅行。" |
| **L2** | 云端混合检索 | 云端 LLM | 派生索引（日期/地名/配文/城市级坐标） | TTL 到期删除 | "我在杭州喜欢什么样的地方？""照着上次那趟规划一个类似周末。" |

### 2.1 为什么是阶梯，不是"全本地"或"全云"

- **全本地不现实**：端侧中文长文本生成的质量、包体、电量都撑不住；把 7B 模型塞进 Capacitor 壳子不是这门课该做的事。
- **全云不成立**：与"本地优先 + 让人相信"的定位直接冲突，而且 2026 年的用户已经不吃"我们很重视隐私"这套话术（微软 Recall 的教训：本地处理都要 opt-in + 可见 + 可删，何况上云）。
- **阶梯的好处**：它把"隐私 vs 能力"从口号变成**可测的曲线**——每一档都能报覆盖率、准确率、成本、外发字节数。这是报告里最能打的一节。

### 2.2 这条路的产品依据

- Booking.com 2025 报告：89% 想用 AI 规划，只有 12% 放心让它独立决策，42% 会反复核对。
- Gartner 2025-06：到 2027 年底超 40% 的 agentic 项目会被取消，原因是成本、价值不清、风控不足；并点名"大多数被包装成 agentic 的用例其实不需要 agentic 实现"。
- ALCE（2024）：GPT-4 在复杂综合任务上约 50% 的陈述没有被引用段落完全支持。

三件事指向同一个结论：**能力已经过剩，可信度才是稀缺品**。阶梯就是"用刚好够的能力，换可核对的外发量"。

## 3. 三条边界与威胁模型

| 边界 | 里面有什么 | 谁能看到 | 主要威胁 | 我们的措施 | **不宣称** |
| --- | --- | --- | --- | --- | --- |
| **Vault（本机）** | 原图、精确 GPS、身份私钥、信物明文、本机索引 | 只有设备持有者 | 设备丢失、共享设备、恶意扩展 | 私钥不导出；信物口令不落库；可一键清空 | 不宣称"设备被攻破也安全" |
| **Engine（服务端，可选）** | 日文档、语义标签、向量、trace | 服务端进程与运维 | 库泄露、日志带原文、模型供应商留存 | 只收派生数据；精确坐标降精度；TTL；按行程 opt-in；小票 | 不宣称"端到端加密"——服务端确实看得到文字 |
| **Gift（朋友间）** | 加密信物、公开的 tag/intensity、签名与承诺 | 指定收件人 | 转发给第三方、收件人截图、元数据侧信道 | 定向 KEM；屏蔽即不打包；界面不报组数；备用钥匙明确标注强度 | 不宣称"防截图"或"绝对不可转发" |

这张表建议**原样放进报告**。课程项目最容易失分的地方不是做得少，而是把"做到了 A"说成"做到了 A+B+C"。

## 4. 路由：什么问题走哪一档

### 4.1 意图分类（客户端规则，先于任何网络请求）

| 意图 | 判定信号 | 档位 | 证据来源 |
| --- | --- | --- | --- |
| 枚举 | "哪些/哪几个/去过哪/几次/哪年/哪次" + 时间或地点 | **L0** | 本机日文档 + 照片 |
| 计数 | "几个/几次/多少/一共/总共" | **L0** | 本机聚合 |
| 偏好统计 | "喜欢什么样/偏好/常去" | **L0** | 标签直方图（复用 TrailShare `fuse`） |
| 求证 | "是不是/有没有/我真的去过吗" | **L0 优先** | 本机匹配 + 时间窗校验 |
| 归纳 | "总结/像在哪/变化" | **L1** | 本机选 3~8 条 → 云端措辞 |
| 综合/规划 | "为什么/帮我规划/比较/建议" | **L2** | 云端混合检索 |

**关键约束：分类必须在客户端完成。** 一旦先把问题发给服务端再决定"要不要上云"，分类本身就已经泄露了问题内容。

### 4.2 升级必须经过同意

```
L0 答不了（证据不足 / 问题超出枚举范围）
   → 弹一张卡：「这个问题需要云端综合。将上传 4 条日文档（2024-10-02 ~ 10-05），
                 不含原图与精确坐标。继续？」
   → [仅这次] [总是允许] [取消]
```

这张卡是整个产品最重要的交互：**它把"隐私"从设置页里的一句说明，变成一个用户每次都能做的决定。**

### 4.3 降级也要说

L2 超时/超预算 → 回退 L1 或 L0，回答照出，小票标 `degraded_reason`。
不允许"静默降级后假装是云端答的"——那是另一种撒谎。

### 5.1 数据小票（设计稿；原实现已于阶段 16 删除）

原代码 `backend/app/privacy/receipt.py` 与 15 条测试已在阶段 16 删除 —— 它没有任何 HTTP 入口。
下面保留字段设计，供真正接线时参考。

```json
{
  "schema_version": "receipt-v1",
  "tier": "L1",
  "sources": { "photo": 4 },
  "docs_sent": 4,
  "bytes_sent": 3182,
  "photos_sent": 0,
  "retention": "none",
  "ttl_hours": null,
  "gift_edges": 0,
  "refused": false,
  "degraded_reason": "",
  "digest": "sha256:…"
}
```

三条硬不变量（构造期就校验，不是文档约定）：

| 不变量 | 违反即报错 |
| --- | --- |
| `photos_sent` 恒为 0，且不是可传参数 | 没有入口能把它写成 1 |
| L0 的 `docs_sent` / `bytes_sent` 必须为 0，`retention=none` | 声称本机却上传，构造失败 |
| L1 必须真的发了文档且 `retention=none`；L2 必须 `retention=ttl` 且有正 `ttl_hours` | "无状态"和"暂存"不能混着说 |

`verify_receipt()` 可以校验一份**外部传入**的小票（字段齐全 → 重建 → 摘要比对）。
**注意口径**：它是自报 + 不变量校验，**不是密码学证明**；服务端仍可能撒谎，小票保证的是"说法自洽、可审计、可逐次对比"。报告里必须这么写。

### 5.2 L1 接口（服务层已实现，HTTP 层待接）

```
POST /api/v1/agent/answer-with-context
```

```json
{
  "query": "这趟和上次那趟像在哪？",
  "session_id": "web-ab12cd34",
  "context": [
    {"doc_id": "d_2024-10-02_wuzhen", "date": "2024-10-02",
     "place": "乌镇", "text": "10-02 乌镇：西栅夜景，临水木屋，江南水乡古镇。"}
  ]
}
```

响应沿用现有 SSE，只是多一个 `receipt` 事件：

```
meta → evidence → delta* → receipt → done
```

实现要点（**不复制主链路**）：

| 复用 | 跳过 |
| --- | --- |
| `BuildContextNode`（`EvidenceBlock` 编号） | `rewrite` / `query_parse`（客户端已做过） |
| `GenerateNode` + `SelfCheckNode` | 向量检索、工具调用、长期记忆 |
| `Trace` / `obs` | 任何写库操作（无状态） |

请求里的 `context` 直接构造成 `EvidenceBlock(index=i+1, ref=DocumentRef("day", doc_id), content=text)`，
`self_check` 的 `[n]` 编号天然对上。**服务端不查库、不落库、不留 session。**

### 5.3 信物接入：只在本机，永不上传

| TrailShare | 主项目 | 映射 |
| --- | --- | --- |
| `Memory`（kind=`gift`） | 本机 `gift_memory` 表（IndexedDB） | 一一对应 |
| `ProvenanceEdge` | `MemorySourceRef(source_type="friend_share")` | `shareId + fromPubkey + signature` 三字段保留 |
| `Tag` 六类 | `utils/semantic_tags.py` 的 `SEMANTIC_TAGS`（阶段 16 起唯一源） | 已一致 |
| `explain()` 的 `[gift:s_xxx]` | 回答里的引用编号 | L0 直接展示；L2 **不注入** |

**硬规则：信物内容不进入 L1/L2 的上传载荷。**
如果用户希望"云端也知道朋友的推荐"，只上传 `{tag, intensity, city}` 三字段的聚合，不上传日期、地点名、照片、签名。

### 5.4 与现有 schema 的映射

| 现有 | 新增 | 说明 |
| --- | --- | --- |
| `DocumentRef.source_type`（trip/place/photo/note） | `day` | L1 的日文档粒度 |
| `MemorySourceRef.source_type` | `friend_share` | 信物来源，仅本机 |
| `ChatMeta`（prompt/embedding/runtime） | `tier` + `receipt` | 前端据此渲染档位徽章 |
| `EvalRow` | `tier` + `docs_sent` + `bytes_sent` | 实验按档位聚合 |

## 6. 界面：六个页面，一个主线

```
① 地图（首页）      旅程卡片 + 地点图钉 + "本机 47 个地点 / 云端索引 0 条"
② 问答              回答卡片：结论句 + 证据条 + 【档位徽章】+【小票】
③ 小票详情          本次用了哪几张照片、发了哪几条、留存多久、可一键删除
④ 信物              TrailShare 的旅程/生成/导入，嵌在同一壳里
⑤ 记忆库            本机记忆 + 朋友分享记忆（不同图标），可评星、可删除
⑥ 设置              "只存本机 / 云端加速"总开关 + 删除云端索引
```

**档位徽章**三态，颜色语义与阶段 7 一致：

| 徽章 | 含义 |
| --- | --- |
| 🟢 本机 | L0，0 条上传 |
| 🔵 薄引擎 | L1，发了 K 条，未留存 |
| 🟠 云引擎 | L2，索引在云端，TTL 24h |
| ⚪ 降级 | 原本要走高档，失败后回退 |

## 7. 三个实验（报告的核心，不是附属）

### E-A 三档对比（必做）

用现有 29 条评测集，逐条标注"最低可行档位"，再跑三档：

| 指标 | L0 | L1 | L2 |
| --- | --- | --- | --- |
| 可回答条数 / 29 | | | |
| 事实正确率 | | | |
| 引用率 | | | |
| P50 / P95 延迟 | | | |
| 单次成本（元） | | | |
| 外发文档条数 | 0 | | |
| 外发字节数 | 0 | | |

**预期结论的正确写法**（无论数字如何）：
> "L0 覆盖了 X% 的问题且外发为 0；剩余问题里，L1 用 Y% 的外发量达到了 L2 的 Z% 准确率。因此我们把默认档设为 L0，只在必要时升级。"

不要写"我们的方案全面优于 RAG"——29 条样本撑不起这句话。

### E-B 小票 A/B（一次课堂问卷即可）

20 位同学，两组各 10 人，同一批问题，一组有票一组没票，问三个 Likert：
"你相信它没有上传原图吗""你愿意把结果分享给朋友吗""你能说清这次数据去了哪吗"。
样本小，只报方向与差值，不报显著性。

### E-C 信物引用忠实度（已有基线）

直接复用 TrailShare E2：平均反事实忠实度 **0.833（5/6）**。
主项目要做的是把它**展示出来**：回答引用 `[gift:s_xxx]` → 点开看到来源与反事实检验按钮。
这条打通了，"两个项目"才变成一个产品。

### 可选 E-D 引用审计

阶段 8 提案里的 claim 级审计，作为 L2 的可选信任层。**不要让它挡住 E-A/E-B/E-C**。

## 10. 明确不做

| 不做 | 理由 |
| --- | --- |
| 端侧大模型 | 包体、电量、中文质量都不划算；L0 用规则就够 |
| 服务端持久化信物 | 一旦上传，"朋友间"这条边界就没了 |
| 实时协作 / 账号体系 | 课程周期内做不完，且与本地优先冲突 |
| 区块链 / 代币 | 单用户没有对手方；TrailShare 的哈希链已经够用 |
| 全量端到端加密 | 服务端要做 RAG 就必须看明文；宣称 E2EE 是造假 |
| 行程规划 Agent | 红海且评测模糊；最多作为 L2 的一个 demo 问题 |

## 11. 答辩问答（提前背）

| 问题 | 回答 |
| --- | --- |
| 这不就是 RAG 加个开关？ | 开关只是表象。三档的差别是**检索位置与数据外发量**，并且每档都有可核对的小票和不变量；RAG 没有"数据去了哪"这个概念。 |
| 为什么不全本地？ | 端侧模型撑不住中文长文本综合；而且很多问题根本不需要模型——L0 用规则答得更准、更快、零外发。 |
| 为什么还留着服务端？ | 综合类问题需要更大的模型和更好的检索。我们做的是"只在必要时、只发必要的数据"，不是"拒绝上云"。 |
| 小票能被伪造吗？ | 能。它是自报 + 不变量校验，不是密码学证明。所以我们同时做了"说法自洽检查"和"逐次可对比"，并在报告里明确这条边界。 |
| 两个项目怎么算一个系统？ | 共用标签体系、来源模型与证据编号；信物是 L0 的一种证据来源；同一张回答卡片同时能引用照片和朋友的推荐。 |
| 创新点是什么？ | 不是"多 Agent"，是**把隐私做成了可测的档位**：同一问题在三档下的覆盖率、准确率、成本、外发量构成一条 Pareto 曲线。 |

## 12. 诚实的局限（报告必须写）

1. 29 条评测集太小，三档对比只能说明方向，不能外推。
2. L0 的规则解析覆盖有限（时间表达、别名、错别字），长尾问题会掉到 L1/L2。
3. 小票是自报，服务端仍可能不照做；没有做远程 attestation。
4. 私钥存在 IndexedDB，未接硬件密钥；换设备等于换身份（TrailShare 已列）。
5. 信物的 tag/intensity 是明文（承诺可验证的代价），能看出"有几组、什么类型"。
6. 没有做真实用户实验，E-B 只有 20 人、方向性结论。
7. L1 的"无状态"靠服务端自律（不写日志/不落库），没有可验证的执行环境。
8. 云端索引一旦开启，服务端确实拥有你的旅行文字史；删除是"接口承诺"，不是"密码学保证"。
