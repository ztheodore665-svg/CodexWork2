## 作品简介

AttackPilot 是面向链上安全事件的攻击复盘平台。用户可以输入单笔或多笔交易 Hash，也可以选择 SushiSwap、ApeCoin 等缓存案例，系统通过链上取证、跨交易分析、动态 Trace 探索、多智能体协作和补丁重放验证，逐步回答“是否存在攻击、攻击路径是什么、根因函数在哪里、修复是否有效”。平台将交易收据、事件日志、资金变化、执行 Trace、合约源码、Agent 日志和验证结果组织成可追溯的结构化报告，服务于安全分析、合约修复和区块链安全教学。作品属于基于区块链真实交易数据的应用系统，重点解决安全人员需要在多个浏览器、Trace 工具和源码页面之间反复切换的问题。

## 开源代码与组件使用情况说明

AttackPilot 的业务代码、前端交互、智能体编排和案例数据由参赛团队完成。项目使用的开源组件及用途如下：

1. React 18、React DOM、React Router、Ant Design、Lucide React、Axios、React Markdown 和 remark-gfm：用于构建前端工作台、任务库、Agent 状态、攻击路径、报告和取证助手界面。
2. Vite 5、TypeScript 5、ESLint 及相关官方插件：用于前端构建、类型检查和代码质量检查。
3. FastAPI、Pydantic、Uvicorn、WebSocket：用于后端接口、数据校验、服务启动和实时任务日志推送。
4. web3.py、eth-abi、eth-utils、Requests、aiohttp、httpx：用于获取和解析 EVM 链上交易、事件、合约及执行数据。
5. MCP/FastMCP、OpenAI Python SDK 和 OpenAI-compatible 模型接口：用于组织工具调用、智能体协作和模型推理。模型输出由团队人工复核，关键结论尽量绑定交易 Hash、Trace 节点、函数位置和补丁重放结果。
6. PostgreSQL、SQLAlchemy、psycopg2-binary、Redis：用于保存任务、结构化报告、日志索引和高频运行时缓存。
7. Docker Compose、PostgreSQL 15、Redis 7：用于本地部署和演示环境编排。
8. Solidity 编译器、solc-typed-ast、Heimdall 等第三方工具：用于合约编译、源码映射和辅助分析；正式提交时仅保留必要的源代码和配置，超大二进制按赛事 100MB 限制处理，并在源文件说明中注明获取方式。

项目参考和数据来源包括 TracePilot、FaultSeeker、DAppFL、DeFiHackLabs、Phalcon、Tenderly、Ethernaut、Solidity 官方文档等，具体授权和链接在设计说明书的参考资料及第三方资源说明中列出。正式上传前应再次核对每项组件的许可证与使用范围。

## 作品安装说明

运行环境：Windows 10/11、Docker Desktop（Docker Compose v2）、Node.js 20 及以上、npm 9 及以上，建议内存 16GB 以上。首次构建需要访问 Docker Hub、npm 和 Python 软件源。

1. 进入 `源代码` 目录，将 `.env.example` 复制为 `backend/.env`，填写一个 OpenAI-compatible 模型服务的 `LLM_NAME`、`LLM_BASE_URL` 和 `LLM_API_KEY`。
2. 在 `源代码` 目录执行 `./Start.ps1`。脚本会启动 PostgreSQL、Redis 和后端服务，导入缓存任务与日志，再安装前端依赖并启动前端。
3. 浏览器访问 `http://localhost:5173`；后端接口文档访问 `http://localhost:8000/docs`。
4. 未填写模型密钥时，仍可打开已导入的 SushiSwap、ApeCoin 等缓存案例；创建新的智能分析任务需要有效的模型服务密钥。
5. 若无法使用一键脚本，可先在 `源代码/backend` 执行 `docker compose up -d --build`，再在 `源代码/deployment` 执行 `./import-demo-data.ps1 -ComposeDirectory ../backend`，最后在 `源代码/frontend` 执行 `npm ci` 和 `npm run dev`。

注意：当前项目源代码中的 `backend/settings.py` 含有硬编码接口凭据，正式交付前必须替换为环境变量并轮换原凭据；作品包不得上传真实密钥。

## 设计思路

AttackPilot 以“交易取证—智能体分析—补丁验证—证据归档”为主线，把安全专家的“提出假设、查找证据、验证结论、修正判断”过程转化为可观察、可恢复的多智能体任务。系统先从交易收据、事件日志、资金流、执行 Trace 和合约源码中建立证据，再由宏观分析智能体识别攻击角色、交易关系和状态依赖，由 Trace 智能体选择性展开可疑调用，最后由补丁智能体生成修复建议并在模拟环境中重放攻击交易。审查智能体检查证据完整性和验证结果，只有在结论达到可解释、可复核的程度后才生成结构化报告。历史报告还会沉淀为可检索的漏洞和案例知识，服务于后续分析与教学。

## 设计重点与难点

1. 跨交易攻击并非单笔交易问题：准备、触发、套利和清理可能分散在多笔交易中。平台通过地址角色、资金变化、入口函数、调用层级和关键操作建立逻辑关联，避免只按时间或金额粗略筛选。
2. 完整 Trace 信息量大且噪声高：平台先建立浅层执行视图，再由智能体围绕资产异常、权限判断、价格计算和状态读写等可疑节点动态展开，保留证据同时控制上下文规模。
3. 模型推理容易产生无法执行的修复建议：平台将补丁编译与攻击重放作为反馈环，区分补丁实现问题和根因判断问题，推动智能体回到前序阶段修正。
4. 长时间任务需要可恢复：平台用 PostgreSQL 保存任务和报告，用 Redis 缓存高频日志和上下文，前端通过 WebSocket 展示实时状态，并支持历史日志分页、任务归档和浏览器断线后的结果恢复。
5. 结论必须可核对：报告尽量把结论绑定到交易 Hash、Trace 节点、函数源码、状态变化、工具调用和补丁验证状态，用户可以通过审查视图和取证助手继续追问。
